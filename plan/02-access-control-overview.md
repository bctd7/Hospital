# 权限业务概览

> 文档状态：讨论草案
>
> 参考：`Medicine/docs/plans/00-overall-framework.md`

## 1. 为什么需要权限

Hospital 同时面向患者和平台管理人员。两类用户看到的数据、能够执行的操作以及承担的责任不同，因此系统必须先建立基本权限边界。

权限需要解决三个最基本的问题：

1. 当前使用者是谁；
2. 当前使用者可以执行哪些操作；
3. 当前使用者可以访问哪些数据。

## 2. 初步用户类型

首期可以先按两类用户理解：

- **账号使用者**：通过微信或其他方式登录，管理本人或被授权的就诊人。
- **就诊人**：预约、检查方案和报告真正对应的人，不一定亲自操作账号。
- **医院工作人员**：在所属医院、院区或科室内处理预约、检查执行、规则和报告等业务。
- **平台管理员**：管理平台级机构、公共配置、账号和系统运行。

医院工作人员后续可能进一步拆分为医院管理员、科室管理员、检查人员、规则编辑、规则审核、客服和审计等角色，但首期不必立即确定完整角色体系。

## 3. 初步权限原则

- 账号使用者只能访问本人或已获得有效授权的就诊人数据；
- 普通患者不能进入管理功能；
- 医院工作人员只能执行岗位允许的操作，并受到医院、院区和科室数据范围限制；
- 平台管理员不应因为拥有平台配置权限就默认可以查看全部患者报告；
- 规则发布、停用和权限变更等关键操作需要留下审计记录；
- 前端隐藏按钮不等于权限控制，最终判断必须由后端完成；
- 默认不允许访问，只有明确授权后才开放；
- 权限设计不应依赖单个页面，未来增加 Web 或 App 时仍可复用。

## 4. RBAC 的初步定位

项目后续可以采用 RBAC，即把若干操作能力组合成角色，再把角色授予用户。

```text
用户 -> 角色 -> 可执行的操作
```

RBAC 适合管理“患者能否创建方案”“管理员能否发布规则”等能力。但患者能否查看某一份具体方案，还需要额外判断该方案是否属于本人。

因此后续设计时需要同时考虑：

- 角色与操作能力；
- 患者数据所有权；
- 管理员可以管理的数据范围；
- 关键操作审计。

## 5. 权限需要考虑的业务维度

权限不能只分“患者”和“管理员”。随着预约和报告业务加入，至少需要从以下维度讨论：

### 5.1 功能权限

决定能否执行预约处理、规则编辑、规则发布、报告发布、人员管理等业务动作。

### 5.2 组织范围

可以形成以下层级：

```text
平台 -> 医院 -> 院区 -> 科室
```

工作人员可能只属于一个科室，也可能跨多个科室工作。医院管理员可以管理全院业务，科室管理员只管理本科室，平台人员只管理平台配置。

是否按科室划分，取决于业务对象是否天然归属于科室。预约订单、检查项目、工作人员和报告通常都可能有科室归属，因此应当预留科室范围，但不必现在固定所有层级。

### 5.3 数据所有权与代理关系

账号和就诊人不是同一个概念。一个账号可能为本人、子女、父母或其他被授权人员办理业务。系统需要表达代理关系、授权来源、有效期和可执行范围。

### 5.4 业务状态

同一个角色在不同状态下能执行的动作不同。例如预约确认后是否还能取消、报告发布后谁可以更正、规则发布后是否允许直接编辑，都需要由业务状态限制。

### 5.5 数据敏感程度

账号资料、预约信息、检查方案和检验报告的敏感程度不同。工作人员能够处理预约，不代表其可以查看完整报告；客服能够联系患者，也不代表其可以查看医学内容。

### 5.6 服务身份

医院接口同步程序、报告连接器和异步任务也需要身份。系统服务的权限应与人员账号分开，且只授予完成任务所需的最小范围。

## 6. 可能出现的角色方向

| 角色方向 | 可能负责的业务 | 可能的数据范围 |
|---|---|---|
| 患者/代办人 | 就诊人、预约、方案、报告 | 本人或被授权就诊人 |
| 科室工作人员 | 预约确认、报到、执行状态 | 所属科室 |
| 科室管理员 | 科室人员、项目和号源 | 所属科室或指定科室 |
| 医院管理员 | 院区、科室和医院级配置 | 所属医院 |
| 规则编辑 | 录入和修改规则草稿 | 指定医院或规则范围 |
| 规则审核 | 审核、发布和停用规则 | 指定医院或平台级范围 |
| 报告工作人员 | 报告匹配、发布、更正 | 指定科室和报告类型 |
| 客服 | 处理预约与账号工单 | 必要的最小患者信息 |
| 审计人员 | 查看关键操作记录 | 指定组织范围，只读 |
| 平台管理员 | 机构、账号和平台配置 | 平台配置，不默认包含医疗数据 |

这些只是业务角色方向，后续可以根据客户实际人员组织进行合并或拆分。

## 7. 是否需要独立权限服务

目前不需要。权限首先是所有业务模块共同遵守的一套规则，可以由公共认证授权代码和身份业务模块共同完成。

只有未来出现多医院、多组织、多系统共享账号或非常复杂的授权策略时，再讨论是否建立独立权限服务。

## 8. 首期建议范围

首期只保证：

- 患者和工作人员能够登录；
- 账号只能操作本人或已授权就诊人的业务；
- 管理接口不能被患者访问；
- 工作人员的数据范围至少可以按医院或科室限制；
- 规则、报告和权限等关键操作可以追溯；
- 权限结构能够支持以后增加更多角色。

复杂权限配置页面、多级组织、多人审批和跨医院授权可以后续讨论。

## 9. 后续需要讨论的问题

1. 客户实际包含哪些医院、院区和科室；
2. 工作人员是严格归属单一科室，还是允许跨科室；
3. 医院管理员、科室管理员和平台管理员分别管理什么；
4. 录入规则和发布规则是否必须由不同人员完成；
5. 哪些人员可以处理预约、查看方案和接触报告；
6. 一个账号是否可以为家属创建预约并查看报告；
7. 家属代办授权如何建立、确认、过期和撤销；
8. 报告是否需要比预约信息更严格的访问控制；
9. 客服处理问题时最少需要看到哪些信息；
10. 哪些操作必须进入审计记录；
11. 用户离职、调岗、禁用或权限撤销后应当立即产生什么效果。

这些问题明确后，再设计详细的角色、能力、数据表和接口。
