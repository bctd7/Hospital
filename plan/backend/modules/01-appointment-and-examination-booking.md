# 01 Appointment 预约检查服务

> 互相独立；科室分别配置上午/下午到院

## 1. 业务目标

完整业务闭环为：

```text
已验证手机号对应的本人账号/档案
  -> 选择一个检查项目
  -> 选择科室配置的日期与上午/下午窗口
  -> 确认预约并占用一个活动容量
  -> 对多条独立检查计算建议执行顺序
  -> 到院报到
  -> 进入科室队列
  -> 工作人员叫号
  -> 医生开始检查
  -> 医生结束检查并释放活动容量
  -> 生成并发布该次检查报告
  -> 患者查看报告
```

Appointment Service 负责检查项目目录、项目和科室/地点的关系、预约窗口、活动容量、预约、报到、排队、
叫号和检查执行状态。报告是完整闭环的必需能力，其正文、附件、版本、发布和更正边界在本 Plan 评审后
继续细化，不能从总体路线中删除。

## 2. 已确定的业务口径

### 2.1 本人身份

- 首期本人档案按照已验证手机号创建或匹配；一个有效手机号对应当前本人的账号和档案；
- 微信 OpenID 和展示昵称不能独立作为预约本人依据；
- 数据库不保存明文手机号，继续使用 Identity 已有的账号、手机号指纹和脱敏值；
- Appointment 保存可稳定关联当前本人的内部 ID。这个 ID 最终复用 `account_id`，还是由手机号对应的本人
  档案生成 `patient_profile_id`，在契约设计前结合手机号换绑和历史归属规则确认；
- 无论最终使用哪个内部 ID，患者查询、取消和查看报告时都必须验证其属于当前已登录手机号对应的本人。

这里不否定手机号的业务作用：手机号是首期本人档案的建立和匹配依据；内部 ID 只是为了避免在预约、
状态历史和报告表中重复保存明文手机号。

### 2.2 独立预约

- 一次预约只包含一个检查项目和一个到院窗口；
- 每次预约拥有独立状态、容量占用、取消结果、失约结果、执行记录和报告关联；
- 同一患者可以同时预约多个检查项目；
- 同一检查项目可以同时存在多条有效预约；
- 同一天可以创建多条预约；
- 不同预约的窗口可以重叠；
- 创建新预约不会自动取消、合并或修改已有预约；
- 系统可以提示已有相同项目或重叠预约，但提示不构成创建限制；是否展示提示不阻塞后端实现；
- 每条创建成功的预约独立计入方案 A 的周期创建额度；取消不返还当期创建次数；
- 系统可以对患者选中的多条独立检查计算建议执行顺序，但顺序结果不合并预约，也不自动创建、取消或
  修改任何预约。

因此当前业务不需要预约总订单、多项目原子确认或独立 Planning Service。数据库聚合根仍是一条独立预约；
检查顺序是 Appointment 内部的建议计算能力，不是跨预约事务或必须遵守的持久化总方案。

### 2.3 取消而非改签

不提供独立改签命令。患者需要更换时间时可以：

```text
先创建新的独立预约
  -> 新预约成功后
  -> 自行决定是否取消旧预约
```

两条预约互不影响。旧预约未取消则继续占用活动容量；新旧预约都分别计入方案 A 的周期创建额度。
系统不提供跨预约事务，也不承担自动释放旧预约的责任。

## 3. 检查项目及检查前置条件

### 3.1 检查项目归属

当前讨论中的“疾病”指患者能够预约的检查项目，不是病历、诊断或患者主诉。后端统一使用“检查项目”
术语，避免将腹部超声、血常规等可执行项目误建模为疾病诊断。

检查项目暂由 Appointment Service 的检查目录拥有，因为它直接决定：

- 患者预约什么；
- 由哪个科室、院区和地点执行；
- 可以选择哪些窗口；
- 预约前需要了解和遵守哪些条件；
- 检查执行记录和报告关联哪个项目。

如果以后检查目录同时成为收费、医嘱、临床知识等多个独立领域的事实源，再评估拆出独立目录服务；当前
不把检查项目放入 Identity，也不为了可能拆分提前创建空服务。

### 3.2 检查前置条件

每个检查项目可以有预约前必须了解的基础条件，例如禁食、禁水、提前停用某类物品、携带资料或到院前
完成某项准备。首期不采集患者自身疾病、用药、年龄、性别、妊娠等个体条件，也不根据个人情况自动作出
医学判断。

前置条件至少需要支持：

- 面向患者的说明；
- 是否必须确认已知晓；
- 生效版本和发布时间；
- 预约时保存当时版本与内容快照；
- 项目要求变化后不篡改历史预约；
- 未来可增加系统可判断的结构化条件，而不破坏已有数据。

### 3.3 首期固态计算语义

首期不设计任意 DSL、动态 Evaluator 或通用知识三元组。所有参与自动排序的规则必须落入以下固定模型：

```text
某个事件发生
  -> 在相对该事件的一段时间区间内
  -> 允许或禁止执行某个目标检查
```

固定约束模式：

| 模式 | 固定语义 |
|---|---|
| `forbid` | 从触发事件起的指定区间内禁止执行目标检查 |
| `allow` | 目标检查只能在触发事件后的指定区间内执行；事件未发生时不可执行 |
| `not_before` | 目标检查不能早于触发事件加偏移量 |
| `not_after` | 目标检查不能晚于触发事件加偏移量 |

首期固定触发事件：

- `food_intake`：进食；
- `water_intake`：饮水；
- `preparation_completed`：指定准备动作完成；
- `examination_started`：指定检查开始；
- `examination_completed`：指定检查结束。

首期固定时间单位为分钟，数据库统一保存整数分钟偏移，不接受自由单位字符串。自然日边界、医院营业日等
日历语义不进入第一版计算；无法转换成上述固定时间约束的规则只作为患者说明或人工确认，不参与自动排序。

示例：进食后 8 小时内不能执行检查 C：

```text
trigger_event = food_intake
target_item = C
mode = forbid
start_offset_minutes = 0
end_offset_minutes = 480
```

示例：进食后 2 小时内才能执行检查 B：

```text
trigger_event = food_intake
target_item = B
mode = allow
start_offset_minutes = 0
end_offset_minutes = 120
```

示例：A 完成 30 分钟后才能执行 B：

```text
trigger_event = examination_completed
trigger_item = A
target_item = B
mode = not_before
start_offset_minutes = 30
```

“B 需要先吃东西、C 需要空腹”不直接建成固定的 `B -> C` 或 `C -> B` 边。进食动作分别触发 B 的允许
区间和 C 的禁止区间；排序求解器再结合 A 等其他检查、科室窗口和移动时间，判断是先完成 C，还是在等待期间
插入 A。这样保存的是可组合的医学时间事实，具体顺序由当次输入计算。

### 3.4 固态关系模型

首期使用 MySQL 关系表保存版本化图事实，不引入图数据库。逻辑图包含：

- 检查项目节点；
- 可插入流程的准备动作节点；
- 由固定时间语义形成的有向约束边；
- 科室窗口和地点作为调度输入，不复制为医学规则边。

概念表固定为：

```text
examination_items
  item_id
  name
  estimated_duration_minutes
  status
  version

preparation_actions
  action_id
  event_type
  name
  estimated_duration_minutes
  status

examination_rule_sets
  rule_set_id
  version
  status                 draft | published | retired
  created_by
  reviewed_by
  published_at

examination_temporal_constraints
  constraint_id
  rule_set_id
  trigger_event_type
  trigger_item_id        nullable
  trigger_action_id      nullable
  target_item_id
  constraint_mode
  start_offset_minutes
  end_offset_minutes     nullable
  patient_instruction
  status
```

数据库约束必须保证：

- 触发源只能是一个明确的准备动作或检查项目；
- `forbid/allow` 必须有结束偏移，且结束偏移不小于开始偏移；
- `not_before/not_after` 只使用一个边界偏移；
- 检查项目、动作和规则停用不删除历史版本；
- 只有 `published` 规则集参与患者侧计算；
- 预约和顺序计算保存所用规则集版本及患者展示说明快照。

建议顺序作为可复现的计算结果保存，而不是预约聚合根：

```text
examination_schedule_runs
  run_id
  patient_id
  rule_set_id
  algorithm_version
  input_snapshot
  objective_snapshot
  created_at

examination_schedule_steps
  run_id
  step_no
  node_type              examination | preparation
  item_id                nullable
  action_id              nullable
  estimated_start_at
  estimated_end_at
  location_id            nullable
  explanation_snapshot
```

计算记录只用于展示、解释和复现，不锁定资源，也不成为检查必须按该顺序执行的业务状态。

这不是完全通用的知识图谱：节点和边具有固定类型和可执行语义，以便数据库校验、管理端编辑、算法计算、
测试和历史复现。

### 3.5 时间区间计算

对每个候选检查，调度器计算：

```text
基础可执行区间 = 科室到院窗口
允许区间       = 所有已触发 allow/not_before/not_after 约束的交集
禁止区间       = 所有已触发 forbid 约束的并集
可执行区间     = 基础可执行区间 ∩ 允许区间 - 禁止区间
```

再结合地图移动时间：

```text
最早到达时间 = 当前时间 + 当前地点到目标地点的移动时间
最早开始时间 = 可执行区间内不早于最早到达时间的第一个时间点
结束时间     = 最早开始时间 + 检查预计耗时
```

地图保持独立地点图，只向排序计算提供地点间预计移动时间。地图变化不修改检查规则，检查规则变化也不修改
地图结构。

### 3.6 首期排序求解器

首期固定搜索问题，不固定唯一搜索算法。所有实现共用以下状态和状态转移：

```text
state
  completed_items
  completed_actions
  current_time
  current_location
  event_times
  accumulated_wait
  accumulated_travel

EXPAND(state)
  -> 枚举尚未完成的检查/准备动作
  -> 根据固定时间约束求最早可执行时间
  -> 校验科室窗口和地图到达时间
  -> 更新事件、时间、地点和已完成集合
  -> 交给具体求解算法继续搜索
  -> 全部完成后比较方案
```

优化目标按固定优先级比较，不先把不同指标随意加权：

1. 必须满足全部硬约束；
2. 完成全部检查的时间最早；
3. 总等待时间最少；
4. 总移动时间最少；
5. 最后按稳定 `item_id` 保证相同输入得到相同结果。

首期允许直接选择以下任一精确求解方式：

- DFS + 分支限界：作为最简单的正确性基线和小规模实现；
- 记忆化动态规划：按已完成集合、当前位置和仍生效的事件窗口保存非支配状态，复用重复子问题；
- A*：使用“剩余检查最短总耗时 + 不可避免的最小移动/等待”作为不得高估的下界，优先扩展最有希望的状态；
- 混合方式：A* 负责搜索顺序，同时使用动态规划式记忆化和状态支配剪枝。

算法选型不是人工业务评审项。在技术设计阶段使用固定案例集和目标规模做基准，至少比较正确性、最优性、
峰值内存和响应时间；可以首期直接采用动态规划、A* 或混合方式，不要求先上线 DFS。无论选哪种实现，均须：

- 满足同一固定状态转移和字典序优化目标；
- 对相同输入产生确定结果；
- 保存 `algorithm_version`、规则版本和输入快照；
- 通过小规模穷举基准验证最优结果；
- 若达到计算预算仍未证明最优，不得把当前候选伪装成“最优方案”，必须明确返回可行但未证明最优或计算失败。

这些算法只替换求解策略，不改变规则表、时间约束语义或预约状态。

排序输入可以是尚未预约的候选检查，也可以是已经独立预约的检查。输出只包含建议顺序、预计开始/结束、
移动/等待摘要、使用的规则版本和解释，不自动占用窗口容量，也不修改独立预约。

### 3.7 后续动态扩展

未来如果固定语义确实不足，再在保持历史兼容的前提下扩展：

- 将触发事件和目标从固定类型扩展为受 Schema 校验的类型注册表；
- 允许检查类别或标签作为目标选择器，减少重复规则；
- 增加版本化参数 JSON，但核心关联、规则状态和版本仍保留关系字段；
- 通过版本化 Evaluator 增加新的计算语义；
- 使用 DSL 组合既有原语；
- 固定语义无法表达或规模数据证明必要时，再评估约束规划、通用规则引擎或图数据库。

动态扩展必须 fail-closed：服务无法识别的硬规则不能被静默忽略。任何新语义都必须定义参数 Schema、计算
实现、解释文本、规则案例和版本；旧规则继续绑定旧语义版本，不能因代码升级改变历史结果。

## 4. 科室到院窗口

### 4.1 窗口定义

预约承诺是某日的上午或下午到院窗口，不承诺精确到分钟的检查开始时间，也不允许患者选择具体医生。
`morning` 和 `afternoon` 只是患者可理解的标签；每个科室/检查项目/地点自行配置具体时间，不能全院写死。

每个窗口至少表达：

```text
检查项目
+ 医院/院区
+ 科室
+ 检查地点
+ 服务日期
+ morning | afternoon
+ 到院开始时间
+ 停止新增预约时间
+ 窗口结束时间
+ 活动容量上限
+ 窗口状态
```

时间必须满足：

```text
start_at <= booking_cutoff_at < end_at
```

例如超声科可以配置上午 `08:00—11:30`、`10:30` 停止新增；放射科可以配置上午
`08:30—12:00`、`11:00` 停止新增。两者不要求相同。

### 4.2 窗口状态

```text
draft -> open -> closed
          |
          +-> suspended -> open | closed
```

- `draft`：尚未开放；
- `open`：当前时间未到停止新增时间且活动容量未满时可以预约；
- `suspended`：临时停止新增，保留已有预约和队列；
- `closed`：永久停止新增，不可重新开放。

暂停、关闭、项目停用、科室停用或地点关闭不能静默取消已有预约。医院需要取消时必须逐条形成业务状态、
取消原因、审计和通知，而且医院原因不能计入患者惩罚。

## 5. 活动容量模型

### 5.1 容量含义

容量不是“整个上午最多服务多少人”，而是该检查窗口允许同时存在的未释放预约数量，类似一个由预约者
占用、由取消/失约处理或医生完成检查释放的计数资源。

```text
0 <= active_occupancy <= active_capacity
available_capacity = active_capacity - active_occupancy
```

占用活动容量的状态：

- `confirmed`：已预约；
- `checked_in`：已报到；
- `queued`：排队中；
- `called`：已叫号；
- `in_progress`：检查中。

释放活动容量的状态：

- `cancelled_by_patient`：患者取消；
- `cancelled_by_hospital`：医院取消；
- `no_show`：确认失约；
- `completed`：医生结束检查。

在停止新增时间之前，容量释放后可以被新的预约继续占用；到达 `booking_cutoff_at` 后，无论是否有空余
容量，都不再接受新预约。这样医生完成检查仍会恢复内部容量计数，但不会在窗口临近结束时重新开放预约。

### 5.2 容量事务

创建预约在同一数据库事务中：

1. 验证本人身份、预约限制和项目可用性；
2. 验证窗口为 `open` 且当前时间早于 `booking_cutoff_at`；
3. 原子检查并增加活动占用；
4. 创建 `confirmed` 预约；
5. 写状态历史、审计、幂等结果和 Outbox；
6. 一次提交。

患者取消、医院取消、确认失约和医生结束检查都必须在事务中锁定预约，确保同一预约最多释放一次容量。
重复完成、重复取消、完成与取消并发不能导致负数或重复释放。

工作人员不能将活动容量上限调低到当前占用以下。窗口时间、停止新增时间和容量的修改规则，以及窗口
开始后是否允许修改，仍需在管理端流程评审时补充。

## 6. 预约、叫号和检查执行状态

当前目标状态机为：

```text
confirmed -> checked_in -> queued -> called -> in_progress -> completed
    |             |          |
    |             +----------+-> no_show / missed_call（细则待确认）
    |
    +-> cancelled_by_patient
    +-> cancelled_by_hospital
    +-> no_show
```

已确定规则：

- 患者预约成功后立即进入 `confirmed` 并占用活动容量；
- 报到、排队、叫号和检查中继续占用容量；
- 医生执行“结束检查”进入 `completed` 并释放容量；
- 医院取消和患者取消必须使用不同状态或稳定原因，只有患者责任行为参与惩罚；
- 预约之间独立，一个预约的状态不能自动修改另一个预约；
- 所有状态变化追加历史，不能覆盖已经发生的事实。

仍需与客户确认：

- 报到开放时间和最晚报到时间；
- 队列是按报到顺序、预约创建顺序还是人工排序；
- 叫号后多久算过号，过号是重新排队还是直接失约；
- 工作人员能否跳号、优先叫号以及必须记录什么原因；
- 窗口结束时仍在队列中的预约如何处理；
- 检查开始后异常中止、重新检查和纠错流程；
- 哪些状态可以由系统自动转换，哪些必须由工作人员确认。

## 7. 报告能力

报告必须进入完整项目范围，并与一次独立预约和实际检查执行记录关联：

```text
completed
  -> report_pending
  -> report_published
  -> report_corrected | report_withdrawn
```

当前已确定：

- 检查完成与报告发布是两个不同事实；完成检查立即释放活动容量，不等待报告；
- 每份报告必须能追溯到患者、预约、检查项目和执行记录；
- 患者只能查看本人报告；发布、更正、撤回、下载和导出需要独立权限和审计；
- 报告更正不能覆盖历史版本。

仍待讨论：报告由本系统录入还是从医院现有报告系统同步；正文和结构化指标的表达；图片/附件格式；
签署和审核流程；发布时间；更正与撤回规则；患者通知；保留期限。根据讨论结果再决定 Report 是
Appointment 内部模块还是独立服务，但不能从业务闭环中删除。

## 8. 预约限制与惩罚方案 A/B/C

这里的 A/B/C 只表示惩罚机制，不是前文已经确定的预约时间模型。客户已经选择方案 A；方案 B/C 仅保留
为未采用的备选记录。相同项目多次预约、同日多次预约和时间窗口重叠始终允许；每条预约分别计入额度。

### 8.1 三套方案共同规则

- 医院取消、窗口关闭、设备或系统故障、工作人员操作错误不计患者责任；
- 同一 `operation_id` 的网络重试不能重复计数；
- 医院责任和患者责任必须使用不同状态或稳定原因码；
- 患者应能看到当前额度、限制原因和恢复时间；
- 人工豁免、加黑、解禁和修改处罚结果都要求专门 permission、原因和审计；
- 永久黑名单不由普通自动规则直接产生，只能人工审核；
- 业务预约限制与 API 防刷限流是两套机制，使用不同统计和错误语义。

### 8.2 方案 A：固定预约额度（已选择）

只限制预约数量，不建立信用积分，也不自动加入黑名单。

```text
创建预约
  -> 检查本周已创建数量
  -> 检查当前未释放预约数量
  -> 未超过额度则允许，超过则拒绝
```

可配置参数：

- 每个自然周最多创建 `A1` 条预约；
- 同时最多持有 `A2` 条未释放预约；
- 最多提前 `A3` 天预约；
- 是否按全院统一，或为科室/稀缺检查项目设置更小额度。

取消、失约和正常完成都不会改变下一周期额度，也不会延长处罚；但已经创建的预约仍计入创建次数，取消后
不返还本周次数，避免通过反复创建和取消绕过上限。

优点：规则简单、容易解释和实现，不需要维护信用状态。缺点：无法区分正常患者和多次失约患者；固定
额度可能限制确有多项检查需求的人，也可能无法充分阻止恶意占用。

### 8.3 方案 B：信用积分与分级限制（未选择）

每个患者维护一个可恢复的预约信用分，不同责任事件扣不同分，并根据分数进入不同限制等级。

示例流程：

```text
初始信用 100
  -> 临近取消：扣 B1 分
  -> 确认失约：扣 B2 分
  -> 叫号后未响应并被认定过号：扣 B3 分
  -> 正常完成：恢复 B4 分（不超过 100）

信用 >= 80       正常额度
信用 60—79       降低每周/同时有效预约额度
信用 40—59       只能预约较近日期或部分项目
信用 < 40         临时冻结 B5 天
```

可配置参数包括事件分值、各等级阈值、每级额度、最长提前预约天数、是否随时间恢复、正常完成恢复分值和
临时冻结天数。原始事件永久保留，信用计算按照规则版本和滚动周期进行。

优点：能够区分行为严重程度，处罚渐进且可通过正常履约恢复。缺点：规则最多、客户解释成本和测试成本
最高；分值和阈值设计不当会让患者难以理解为什么被限制。

### 8.4 方案 C：失约次数触发自动临时黑名单（未选择）

不计算连续信用分，只统计滚动周期内的责任事件次数。达到阈值后自动进入有期限的预约黑名单。

示例流程：

```text
滚动 C1 天内
  -> 确认失约累计 C2 次
  -> 或临近取消累计 C3 次折算为一次失约
  -> 自动进入临时黑名单 C4 天
  -> 黑名单期间禁止创建新预约
  -> 到期自动解除；再次触发时限制期可递增
```

可配置参数包括滚动周期、失约阈值、临近取消折算规则、首次限制天数、重复触发是否递增、最长限制天数和
是否允许工作人员提前解禁。系统必须通知患者触发依据、起止时间和申诉方式。

优点：比积分方案简单，能够直接处理反复失约，规则也容易向客户和患者说明。缺点：阈值附近存在跳变，
轻重行为难以精细区分；失约认定错误会立即影响预约资格，因此必须有复核和申诉。

这里的“自动黑名单”只指有明确到期时间的临时限制。长期或永久黑名单必须由有权限的工作人员查看证据后
人工决定，不能仅凭手机号累计次数永久封禁。

### 8.5 方案对比

| 对比项 | 方案 A：固定额度 | 方案 B：信用积分 | 方案 C：临时黑名单 |
|---|---|---|---|
| 核心控制 | 周期预约数、同时有效数 | 行为扣分和分级额度 | 滚动周期责任事件次数 |
| 是否区分行为严重度 | 否 | 是，最精细 | 部分区分，可按事件折算 |
| 是否自动冻结 | 否 | 低分后临时冻结 | 达阈值立即临时冻结 |
| 是否自动黑名单 | 否 | 通常不需要 | 是，但必须有期限 |
| 正常完成能否恢复 | 下一周期恢复额度 | 可恢复信用分 | 不抵消事件，等待滚动过期 |
| 患者解释难度 | 低 | 高 | 中 |
| 实现和测试成本 | 低 | 高 | 中 |
| 适合场景 | 先控制总量、规则尽量简单 | 希望长期精细运营 | 重点治理多次失约 |

### 8.6 方案 A 参数确认单

方案 A 已经选定，客户继续填写其参数。方案 B/C 的积分、黑名单、信用恢复和自动冻结参数不进入首期：

| 决策 | 客户选择 |
|---|---|
| 首期采用方案 | **A 固定预约额度（已确认）** |
| 统计周期 | 建议自然周；待客户确认 |
| 每周创建上限 `A1` | 待填写 |
| 同时有效预约上限 `A2` | 待填写 |
| 最长提前预约天数 `A3` | 待填写 |
| 免费取消截止 | 窗口开始前多少小时；或按项目配置 |
| 临近取消是否记录责任事件 | 是 / 否；方案 A 只记录，不自动扣分或加黑 |
| 失约认定 | 系统自动 / 工作人员确认 / 自动后允许申诉 |
| 过号是否属于责任事件 | 是 / 重新排队 / 工作人员决定 |
| 自动限制期限 | 不适用；方案 A 不自动冻结或加黑 |
| 正常完成是否恢复 | 不适用；下一统计周期恢复创建额度 |
| 人工豁免和申诉 | 是否支持、由谁审批、处理时限 |
| 永久黑名单 | 不进入首期方案 A；如未来需要只能人工审核 |

## 9. 幂等、并发和审计

- 每个写操作要求 UUID `operation_id`；同一 ID 和相同请求返回第一次结果，同一 ID 携带不同请求返回冲突；
- 创建预约必须原子检查限制、停止新增时间和活动容量；
- 最后一个活动容量并发预约时只能有一个请求成功；
- 取消、失约和完成最多释放一次容量；
- 处罚事件必须与预约状态事实同事务写入，异步汇总失败不能丢失原始责任事件；
- 黑名单、限制、豁免和解禁必须版本化并产生业务审计；
- 项目、窗口、队列和报告管理写操作使用乐观版本；
- 主数据、状态历史、审计、幂等结果和 Outbox 保持本地事务一致。

## 10. 权限边界

患者只能操作已验证手机号对应的本人预约和报告。工作人员按照当前科室和 permission 操作：

- `appointment.read`：查看授权科室预约和队列；
- `appointment.update`：报到、排队、叫号、开始、完成和失约处理；
- `appointment.cancel`：医院原因取消；
- `appointment.catalog.manage`：维护检查项目、科室/地点关系和前置条件；
- `appointment.capacity.manage`：维护窗口、停止新增时间和活动容量；
- `appointment.restriction.manage`：人工限制、豁免和解禁；
- Report 相关发布、更正、撤回、下载和导出沿用独立权限语义。

`super_admin` 可以跨科室管理，普通工作人员只能操作当前科室。权限通过不能绕过状态机、容量、限制版本
和报告版本。日志不得保存 Token、完整手机号、报告正文或不必要的患者信息。

## 11. 明确不进入当前简化范围

- 精确分钟预约和患者选择具体医生；
- 医生排班；
- 多项目总订单、独立 Planning Service、原子创建多条预约和自动修改已有预约；
- 独立改签事务；
- 支付、退款、医保和医生开单；
- 根据患者疾病、用药、年龄、性别、妊娠等个体条件自动判断检查适用性；
- 任意 DSL、动态 Evaluator、自由三元组或首期无法识别的新计算语义；
- 未经客户确认直接启用自动永久黑名单。

叫号和报告不在排除范围内，必须作为完整闭环继续设计和实施。

## 12. 下一步评审顺序

1. 客户填写方案 A 的预约额度参数；
2. 人工确认首期固定事件、四种时间约束、排序优化目标和规则管理流程；
3. 确认报到、排队、叫号、过号和失约状态机；
4. 确认报告录入/同步、版本、附件、审核和发布流程；
5. 最终确认手机号、`account_id` 与本人档案内部 ID 的关系；
6. 将确认结果继续收敛到本文；
7. 人工批准本文后，才开始权限、HTTP、Proto、事件和迁移契约；
8. 按检查目录 → 窗口容量 → 独立预约 → 建议顺序 → 叫号执行 → 报告的纵向顺序实施。
