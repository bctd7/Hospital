# 01 Appointment 预约检查服务

> 状态：阶段 4 收尾功能已实现；真实 MySQL 集成用例等待本地数据库进程可用后执行。本文是 Appointment Service 当前总 Plan。
>
> 已确定：一个检查项目和一个检查房间都只属于一个科室；管理员按“科室—房间—项目”维护关系，患者按
> “科室—项目—房间”选择。房间开放时间/共享活动容量与项目预约时间/停止新增时间独立配置；每天最多一个
> 自定义 morning 和 afternoon 大窗口，项目窗口必须完整落在房间窗口内。患者只预约当前自然周。
>
> 已选择：预约限制采用惩罚方案 A“固定预约额度”；每名患者每个自然周最多成功预约 10 次，取消、完成和失约不返还。
>
> 已确定：第一实施阶段只把检查前置条件保存在检查项目的 `description` 字符串中，不解析、不参与自动
> 排序。后续可以由受约束的 AI 从指定描述版本提取固定字段，经校验和人工确认后形成“事件触发时间约束图”；
> 求解器可采用 DFS、记忆化动态规划、A* 或其组合。
>
> 报告内容、首版发布和更正规则已经确认并进入阶段 4；首期不引入报到、排队、叫号和过号状态。
>
> 接口字段在评审通过后进入 `contracts/`，本文不提前复制 HTTP、RPC 或数据库字段清单。

## 1. 业务目标

完整业务闭环为：

```text
已验证手机号对应的本人账号/档案
  -> 选择科室和一个检查项目
  -> 选择能够执行该项目的房间
  -> 选择本周日期与上午/下午窗口
  -> 确认预约并占用一个活动容量
  -> 授权科室工作人员在项目时间内开始检查
  -> 医生结束检查并释放活动容量
  -> 生成并发布该次检查报告
  -> 患者查看报告
```

Appointment Service 负责检查项目目录、检查房间、房间—项目关系、两类独立周配置、活动容量、预约、
检查执行状态和报告。首期不负责报到、排队、叫号和医生排班。

## 2. 已确定的业务口径

### 2.1 本人身份

- 首期本人档案按照已验证手机号创建或匹配；一个有效手机号对应当前本人的账号和档案；
- 小程序平台标识和展示昵称不能独立作为预约本人依据；
- 数据库不保存明文手机号，继续使用 Identity 已有的账号、手机号指纹和脱敏值；
- Appointment 保存可稳定关联当前本人的内部 ID。这个 ID 最终复用 `account_id`，还是由手机号对应的本人
  档案生成 `patient_profile_id`，在契约设计前结合手机号换绑和历史归属规则确认；
- 无论最终使用哪个内部 ID，患者查询、取消和查看报告时都必须验证其属于当前已登录手机号对应的本人。

这里不否定手机号的业务作用：手机号是首期本人档案的建立和匹配依据；内部 ID 只是为了避免在预约、
状态历史和报告表中重复保存明文手机号。

### 2.2 独立预约

- 一次预约只包含一个检查项目、一个患者选择的房间和一个本周到院窗口；
- 每次预约拥有独立状态、容量占用、取消结果、失约结果、执行记录和报告关联；
- 同一患者可以同时预约多个检查项目；
- 同一检查项目可以同时存在多条有效预约；
- 同一天可以创建多条预约，但同一上午或下午只能保留一条 `confirmed` 预约；
- 不同预约的窗口可以重叠；
- 患者只能预约当前自然周，后端不自动选择或优化科室、房间和窗口；
- 创建新预约不会自动取消、合并或修改已有预约；
- 系统可以提示已有相同项目或重叠预约，但提示不构成创建限制；是否展示提示不阻塞后端实现；
- 每条创建成功的预约独立计入方案 A 的周期创建额度；取消不返还当期创建次数；
- 系统可以对患者选中的多条独立检查计算建议执行顺序，但顺序结果不合并预约，也不自动创建、取消或
  修改任何预约。

因此当前业务不需要预约总订单、多项目原子确认或独立 Planning Service。数据库聚合根仍是一条独立预约；
检查顺序是 Appointment 内部的建议计算能力，不是跨预约事务或必须遵守的持久化总方案。

### 2.3 取消而非改签

不提供独立改签命令。患者需要更换时间时可以：

```text
先创建新的独立预约
  -> 新预约成功后
  -> 自行决定是否取消旧预约
```

两条预约互不影响。旧预约未取消则继续占用活动容量；新旧预约都分别计入方案 A 的周期创建额度。
系统不提供跨预约事务，也不承担自动释放旧预约的责任。

## 3. 检查项目及检查前置条件

### 3.1 检查项目归属

当前讨论中的“疾病”指患者能够预约的检查项目，不是病历、诊断或患者主诉。后端统一使用“检查项目”
术语，避免将腹部超声、血常规等可执行项目误建模为疾病诊断。

检查项目暂由 Appointment Service 的检查目录拥有，因为它直接决定：

- 患者预约什么；
- 属于哪个唯一科室，以及该科室哪些房间可以执行；
- 可以选择哪些窗口；
- 预约前需要了解和遵守哪些条件；
- 检查执行记录和报告关联哪个项目。

如果以后检查目录同时成为收费、医嘱、临床知识等多个独立领域的事实源，再评估拆出独立目录服务；当前
不把检查项目放入 Identity，也不为了可能拆分提前创建空服务。

### 3.2 检查前置条件

每个检查项目可以有预约前必须了解的基础条件，例如禁食、禁水、提前停用某类物品、携带资料或到院前
完成某项准备。首期不采集患者自身疾病、用药、年龄、性别、妊娠等个体条件，也不根据个人情况自动作出
医学判断。

前置条件至少需要支持：

- 面向患者的说明；
- 是否必须确认已知晓；
- 生效版本和发布时间；
- 预约时保存当时版本与内容快照；
- 项目要求变化后不篡改历史预约；
- 未来可增加系统可判断的结构化条件，而不破坏已有数据。

第一实施阶段采用以下简化模型：

- `description` 是检查项目上的一个 `string` 字段，也是患者当前看到的完整说明；
- 禁食、禁水、准备动作、间隔时间等规则都先嵌入这段自然语言描述；
- 服务只保存、返回和更新描述，不从文本中猜测规则，不据此进行自动排序；
- 每次更新描述都递增检查项目 `version`，历史预约以后保存当时的描述快照；
- 当前不增加空的结构化列、JSON 规则字段或规则表占位。

第一阶段实施细节见
[检查项目描述 CRUD 与服务骨架](./appointment/01-examination-item-description-crud.md)。

### 3.3 后续固定计算语义

进入自动排序阶段后，不直接执行任意自然语言、DSL、动态 Evaluator 或通用知识三元组。所有参与计算的规则
必须先从某个明确的检查项目描述版本提取，并落入以下固定模型：

```text
某个事件发生
  -> 在相对该事件的一段时间区间内
  -> 允许或禁止执行某个目标检查
```

固定约束模式：

| 模式 | 固定语义 |
|---|---|
| `forbid` | 从触发事件起的指定区间内禁止执行目标检查 |
| `allow` | 目标检查只能在触发事件后的指定区间内执行；事件未发生时不可执行 |
| `not_before` | 目标检查不能早于触发事件加偏移量 |
| `not_after` | 目标检查不能晚于触发事件加偏移量 |

第一版结构化模型固定触发事件：

- `food_intake`：进食；
- `water_intake`：饮水；
- `preparation_completed`：指定准备动作完成；
- `examination_started`：指定检查开始；
- `examination_completed`：指定检查结束。

第一版结构化模型固定时间单位为分钟，数据库统一保存整数分钟偏移，不接受自由单位字符串。自然日边界、医院营业日等
日历语义不进入第一版计算；无法转换成上述固定时间约束的规则只作为患者说明或人工确认，不参与自动排序。

示例：进食后 8 小时内不能执行检查 C：

```text
trigger_event = food_intake
target_item = C
mode = forbid
start_offset_minutes = 0
end_offset_minutes = 480
```

示例：进食后 2 小时内才能执行检查 B：

```text
trigger_event = food_intake
target_item = B
mode = allow
start_offset_minutes = 0
end_offset_minutes = 120
```

示例：A 完成 30 分钟后才能执行 B：

```text
trigger_event = examination_completed
trigger_item = A
target_item = B
mode = not_before
start_offset_minutes = 30
```

“B 需要先吃东西、C 需要空腹”不直接建成固定的 `B -> C` 或 `C -> B` 边。进食动作分别触发 B 的允许
区间和 C 的禁止区间；排序求解器再结合 A 等其他检查、患者已选房间和移动时间，判断是先完成 C，还是在等待期间
插入 A。这样保存的是可组合的医学时间事实，具体顺序由当次输入计算。

### 3.4 后续固态关系模型

结构化阶段使用 MySQL 关系表保存版本化图事实，不引入图数据库。逻辑图包含：

- 检查项目节点；
- 可插入流程的准备动作节点；
- 由固定时间语义形成的有向约束边；
- 患者已选房间、项目窗口和房间窗口作为调度输入，不复制为医学规则边。

概念表在进入该阶段前通过独立实施 Plan 和迁移确认；至少包含：

```text
examination_items
  item_id
  name
  estimated_duration_minutes
  status
  version

preparation_actions
  action_id
  event_type
  name
  estimated_duration_minutes
  status

examination_rule_sets
  rule_set_id
  version
  status                 draft | published | retired
  created_by
  reviewed_by
  published_at

examination_temporal_constraints
  constraint_id
  rule_set_id
  trigger_event_type
  trigger_item_id        nullable
  trigger_action_id      nullable
  target_item_id
  constraint_mode
  start_offset_minutes
  end_offset_minutes     nullable
  patient_instruction
  status
```

结构化结果必须记录来源 `item_id`、来源检查项目 `version`、提取 Schema 版本以及审核状态。AI 提取只生成
草稿，不能直接成为患者侧已发布硬约束；检查项目描述更新后，旧提取结果继续保留用于历史复现，但不能
自动套用到新版本。以上字段和表通过后续增量迁移加入，不要求第一阶段提前占位。

数据库约束必须保证：

- 触发源只能是一个明确的准备动作或检查项目；
- `forbid/allow` 必须有结束偏移，且结束偏移不小于开始偏移；
- `not_before/not_after` 只使用一个边界偏移；
- 检查项目、动作和规则停用不删除历史版本；
- 只有 `published` 规则集参与患者侧计算；
- 预约和顺序计算保存所用规则集版本及患者展示说明快照。

建议顺序作为可复现的计算结果保存，而不是预约聚合根：

```text
examination_schedule_runs
  run_id
  patient_id
  rule_set_id
  algorithm_version
  input_snapshot
  objective_snapshot
  created_at

examination_schedule_steps
  run_id
  step_no
  node_type              examination | preparation
  item_id                nullable
  action_id              nullable
  estimated_start_at
  estimated_end_at
  location_id            nullable
  explanation_snapshot
```

计算记录只用于展示、解释和复现，不锁定资源，也不成为检查必须按该顺序执行的业务状态。

这不是完全通用的知识图谱：节点和边具有固定类型和可执行语义，以便数据库校验、管理端编辑、算法计算、
测试和历史复现。

### 3.5 时间区间计算

对每个候选检查，调度器计算：

```text
基础可执行区间 = 患者已选项目窗口（已完整落在房间开放窗口内）
允许区间       = 所有已触发 allow/not_before/not_after 约束的交集
禁止区间       = 所有已触发 forbid 约束的并集
可执行区间     = 基础可执行区间 ∩ 允许区间 - 禁止区间
```

再结合地图移动时间：

```text
最早到达时间 = 当前时间 + 当前地点到目标地点的移动时间
最早开始时间 = 可执行区间内不早于最早到达时间的第一个时间点
结束时间     = 最早开始时间 + 检查预计耗时
```

房间间预计移动时间属于后续检查顺序能力的输入，不要求独立 Navigation Service。空间信息变化不修改检查
规则，检查规则变化也不修改房间主数据。

### 3.6 首期排序求解器

首期固定搜索问题，不固定唯一搜索算法。所有实现共用以下状态和状态转移：

```text
state
  completed_items
  completed_actions
  current_time
  current_location
  event_times
  accumulated_wait
  accumulated_travel

EXPAND(state)
  -> 枚举尚未完成的检查/准备动作
  -> 根据固定时间约束求最早可执行时间
  -> 校验患者已选房间、项目窗口和预计到达时间
  -> 更新事件、时间、地点和已完成集合
  -> 交给具体求解算法继续搜索
  -> 全部完成后比较方案
```

优化目标按固定优先级比较，不先把不同指标随意加权：

1. 必须满足全部硬约束；
2. 完成全部检查的时间最早；
3. 总等待时间最少；
4. 总移动时间最少；
5. 最后按稳定 `item_id` 保证相同输入得到相同结果。

首期允许直接选择以下任一精确求解方式：

- DFS + 分支限界：作为最简单的正确性基线和小规模实现；
- 记忆化动态规划：按已完成集合、当前位置和仍生效的事件窗口保存非支配状态，复用重复子问题；
- A*：使用“剩余检查最短总耗时 + 不可避免的最小移动/等待”作为不得高估的下界，优先扩展最有希望的状态；
- 混合方式：A* 负责搜索顺序，同时使用动态规划式记忆化和状态支配剪枝。

算法选型不是人工业务评审项。在技术设计阶段使用固定案例集和目标规模做基准，至少比较正确性、最优性、
峰值内存和响应时间；进入该阶段时可以直接采用动态规划、A* 或混合方式，不要求先上线 DFS。无论选哪种实现，均须：

- 满足同一固定状态转移和字典序优化目标；
- 对相同输入产生确定结果；
- 保存 `algorithm_version`、规则版本和输入快照；
- 通过小规模穷举基准验证最优结果；
- 若达到计算预算仍未证明最优，不得把当前候选伪装成“最优方案”，必须明确返回可行但未证明最优或计算失败。

这些算法只替换求解策略，不改变规则表、时间约束语义或预约状态。

排序输入可以是尚未预约的候选检查，也可以是已经独立预约的检查。输出只包含建议顺序、预计开始/结束、
移动/等待摘要、使用的规则版本和解释，不自动占用窗口容量，也不修改独立预约。

### 3.7 后续动态扩展

未来如果固定语义确实不足，再在保持历史兼容的前提下扩展：

- 将触发事件和目标从固定类型扩展为受 Schema 校验的类型注册表；
- 允许检查类别或标签作为目标选择器，减少重复规则；
- 增加版本化参数 JSON，但核心关联、规则状态和版本仍保留关系字段；
- 通过版本化 Evaluator 增加新的计算语义；
- 使用 DSL 组合既有原语；
- 固定语义无法表达或规模数据证明必要时，再评估约束规划、通用规则引擎或图数据库。

动态扩展必须 fail-closed：服务无法识别的硬规则不能被静默忽略。任何新语义都必须定义参数 Schema、计算
实现、解释文本、规则案例和版本；旧规则继续绑定旧语义版本，不能因代码升级改变历史结果。

## 4. 检查房间、项目关系与独立周配置

### 4.1 房间和项目关系

一个项目只属于一个科室，一个检查房间也只属于一个科室。一个房间可以执行本部门多个项目，一个项目也
可以在本部门多个房间执行。关系只表达 `room_id + item_id`，不保存医生、时间、容量或重复科室字段。

管理员按“科室—房间—项目”维护，患者按“科室—项目—房间”查询；两者读取同一份关系。房间和项目必须
属于同一科室，跨科室关系始终拒绝。

### 4.2 房间周开放配置

房间分别配置周一至周日的 `morning/afternoon` 开放时间和共享活动容量：

```text
room_id + weekday + session
+ open_time
+ close_time
+ active_capacity
```

### 4.3 项目周预约配置

项目独立配置周一至周日的 `morning/afternoon` 预约时间和停止新增时间：

```text
item_id + weekday + session
+ start_time
+ booking_cutoff_time
+ end_time
```

每天最多一个连续 morning 和一个连续 afternoon，不支持把同一个上午或下午拆成多个小窗口。项目窗口必须
完整落在关联房间对应窗口内，不自动取交集或裁剪。新增关系以及修改房间/项目时间都执行严格校验；任何
active 关系不满足完整包含时拒绝修改并返回冲突资源。

配置没有修改时持续沿用上一周；修改从当前周立即生效并由后续周继续沿用。不实现节假日、单日例外、
未来周预排和医生排班。患者只能预约当前自然周。

### 4.4 配置变更影响

项目、房间或关系停用，以及本周时间缩短后，不能继续执行的已有预约改为 `cancelled_by_hospital`，不计患者
责任，释放一次容量并保留原因、历史和审计；“删除”只表示从有效预约中移除，不物理删除数据库记录。

## 5. 活动容量模型

### 5.1 容量含义

容量属于“房间＋具体服务日期＋morning/afternoon”，由该房间窗口下所有项目共享。容量表示允许同时存在的
未释放预约数量，不是某个项目整个上午最多创建多少预约。

```text
0 <= active_occupancy <= active_capacity
available_capacity = active_capacity - active_occupancy
```

占用活动容量的状态：

- `confirmed`：待检查；
- `in_progress`：检查中。

释放活动容量的状态：

- `cancelled_by_patient`：患者取消；
- `cancelled_by_hospital`：医院取消；
- `no_show`：确认失约；
- `completed`：医生结束检查。

每条预约统一占用一个容量单位，不设置项目权重。在停止新增时间之前，容量释放后可以被同一房间任何可执行
项目继续占用；到达项目 `booking_cutoff_time` 后，即使房间仍开放且有空余容量，也不能新增该项目预约。

### 5.2 容量事务

创建预约在同一数据库事务中：

1. 验证本人身份、预约限制和项目可用性；
2. 验证服务日期在本周、项目窗口完整落在患者所选房间窗口内，且当前时间早于项目停止新增时间；
3. 原子检查并增加活动占用；
4. 创建 `confirmed` 预约；
5. 写状态历史、审计、幂等结果和 Outbox；
6. 一次提交。

患者取消、医院取消、确认失约和医生结束检查都必须在事务中锁定预约，确保同一预约最多释放一次容量。
重复完成、重复取消、完成与取消并发不能导致负数或重复释放。

容量调低到当前占用以下时，系统按 `created_at DESC, appointment_id DESC` 将足够数量的最新 `confirmed`
预约改为 `cancelled_by_hospital`。`in_progress` 预约不能自动取消；取消全部 `confirmed`
后占用仍高于新容量时拒绝调整。

## 6. 预约、叫号和检查执行状态

当前目标状态机为：

```text
confirmed -> in_progress -> completed
    |
    +-> no_show
```

已确定规则：

- 患者预约成功后立即进入 `confirmed` 并占用活动容量；
- 待检查和检查中继续占用容量；
- 医生执行“结束检查”进入 `completed` 并释放容量；
- 工作人员只能在预约项目时间内执行 `confirmed -> in_progress`；
- 项目窗口结束后仍为 `confirmed` 的预约自动进入 `no_show`，释放容量和患者时段占位并保留记录；
- `in_progress` 不因项目窗口结束而自动变化；
- 医院取消和患者取消必须使用不同状态或稳定原因，只有患者责任行为参与惩罚；
- 预约之间独立，一个预约的状态不能自动修改另一个预约；
- 所有状态变化追加历史，不能覆盖已经发生的事实。

首期不引入报到、排队、叫号或过号状态。

## 7. 报告能力

报告位于 Appointment 内部，并与一次独立预约和实际检查执行记录绑定：

```text
confirmed -> in_progress
  -> completed + report version 1 published + capacity released（同一事务）
  -> report version 2...N corrected（新增版本，不覆盖旧版）
```

当前已确定：

- 检查完成与首版报告发布绑定为一个业务动作，在同一事务中完成并释放活动容量；
- 每份报告必须能追溯到患者、预约、检查项目和执行记录；
- 患者只能查看本人当前正式报告；草稿不对患者可见；
- 草稿允许编辑，正式发布后禁止原地修改；
- 更正必须填写原因并创建新版本，旧版保留为可追溯历史；
- 本科室授权医生可录入和发布；实际执行人员优先取预约 `started_by`；
- 首期采用固定字段：检查所见、检查结论、可选处理建议和备注；
- 报告项目名称、院区、楼栋、楼层和房间号使用发布时稳定快照。

后续再讨论图片/附件与 OSS、PDF、电子签章、多级审核、撤回审批、患者通知和保留期限；这些能力不能
改变正式版本不可覆盖和患者只能读取本人当前有效版本的规则。

## 8. 预约限制与惩罚方案 A/B/C

这里的 A/B/C 只表示惩罚机制，不是前文已经确定的预约时间模型。客户已经选择方案 A；方案 B/C 仅保留
为未采用的备选记录。相同项目多次预约、同日多次预约和时间窗口重叠始终允许；每条预约分别计入额度。

### 8.1 三套方案共同规则

- 医院取消、窗口关闭、设备或系统故障、工作人员操作错误不计患者责任；
- 同一 `operation_id` 的网络重试不能重复计数；
- 医院责任和患者责任必须使用不同状态或稳定原因码；
- 患者应能看到当前额度、限制原因和恢复时间；
- 人工豁免、加黑、解禁和修改处罚结果都要求专门 permission、原因和审计；
- 永久黑名单不由普通自动规则直接产生，只能人工审核；
- 业务预约限制与 API 防刷限流是两套机制，使用不同统计和错误语义。

### 8.2 方案 A：固定预约额度（已选择）

只限制预约数量，不建立信用积分，也不自动加入黑名单。

```text
创建预约
  -> 检查本周已创建数量
  -> 未超过额度则允许，超过则拒绝
```

首期固定参数：

- 每个自然周最多成功创建 10 条预约；
- 只能预约当前自然周；
- 不按科室、项目或医生细分额度，也不另设同时有效预约总数。

取消、失约和正常完成都不会改变下一周期额度，也不会延长处罚；但已经创建的预约仍计入创建次数，取消后
不返还本周次数，避免通过反复创建和取消绕过上限。

优点：规则简单、容易解释和实现，不需要维护信用状态。缺点：无法区分正常患者和多次失约患者；固定
额度可能限制确有多项检查需求的人，也可能无法充分阻止恶意占用。

### 8.3 方案 B：信用积分与分级限制（未选择）

每个患者维护一个可恢复的预约信用分，不同责任事件扣不同分，并根据分数进入不同限制等级。

示例流程：

```text
初始信用 100
  -> 临近取消：扣 B1 分
  -> 确认失约：扣 B2 分
  -> 叫号后未响应并被认定过号：扣 B3 分
  -> 正常完成：恢复 B4 分（不超过 100）

信用 >= 80       正常额度
信用 60—79       降低每周/同时有效预约额度
信用 40—59       只能预约较近日期或部分项目
信用 < 40         临时冻结 B5 天
```

可配置参数包括事件分值、各等级阈值、每级额度、最长提前预约天数、是否随时间恢复、正常完成恢复分值和
临时冻结天数。原始事件永久保留，信用计算按照规则版本和滚动周期进行。

优点：能够区分行为严重程度，处罚渐进且可通过正常履约恢复。缺点：规则最多、客户解释成本和测试成本
最高；分值和阈值设计不当会让患者难以理解为什么被限制。

### 8.4 方案 C：失约次数触发自动临时黑名单（未选择）

不计算连续信用分，只统计滚动周期内的责任事件次数。达到阈值后自动进入有期限的预约黑名单。

示例流程：

```text
滚动 C1 天内
  -> 确认失约累计 C2 次
  -> 或临近取消累计 C3 次折算为一次失约
  -> 自动进入临时黑名单 C4 天
  -> 黑名单期间禁止创建新预约
  -> 到期自动解除；再次触发时限制期可递增
```

可配置参数包括滚动周期、失约阈值、临近取消折算规则、首次限制天数、重复触发是否递增、最长限制天数和
是否允许工作人员提前解禁。系统必须通知患者触发依据、起止时间和申诉方式。

优点：比积分方案简单，能够直接处理反复失约，规则也容易向客户和患者说明。缺点：阈值附近存在跳变，
轻重行为难以精细区分；失约认定错误会立即影响预约资格，因此必须有复核和申诉。

这里的“自动黑名单”只指有明确到期时间的临时限制。长期或永久黑名单必须由有权限的工作人员查看证据后
人工决定，不能仅凭手机号累计次数永久封禁。

### 8.5 方案对比

| 对比项 | 方案 A：固定额度 | 方案 B：信用积分 | 方案 C：临时黑名单 |
|---|---|---|---|
| 核心控制 | 周期预约数、同时有效数 | 行为扣分和分级额度 | 滚动周期责任事件次数 |
| 是否区分行为严重度 | 否 | 是，最精细 | 部分区分，可按事件折算 |
| 是否自动冻结 | 否 | 低分后临时冻结 | 达阈值立即临时冻结 |
| 是否自动黑名单 | 否 | 通常不需要 | 是，但必须有期限 |
| 正常完成能否恢复 | 下一周期恢复额度 | 可恢复信用分 | 不抵消事件，等待滚动过期 |
| 患者解释难度 | 低 | 高 | 中 |
| 实现和测试成本 | 低 | 高 | 中 |
| 适合场景 | 先控制总量、规则尽量简单 | 希望长期精细运营 | 重点治理多次失约 |

### 8.6 方案 A 参数确认单

方案 A 已经选定。方案 B/C 的积分、黑名单、信用恢复和自动冻结参数不进入首期：

| 决策 | 客户选择 |
|---|---|
| 首期采用方案 | **A 固定预约额度（已确认）** |
| 统计周期 | **自然周（已确认）** |
| 每周创建上限 | **10（已确认）** |
| 同时有效预约总上限 | 不设置；仅保留同日同上午/下午的一条待检查预约约束 |
| 可预约日期范围 | **仅当前自然周（已确认）** |
| 免费取消截止 | 窗口开始前多少小时；或按项目配置 |
| 临近取消是否记录责任事件 | 是 / 否；方案 A 只记录，不自动扣分或加黑 |
| 失约认定 | 系统自动 / 工作人员确认 / 自动后允许申诉 |
| 过号是否属于责任事件 | 是 / 重新排队 / 工作人员决定 |
| 自动限制期限 | 不适用；方案 A 不自动冻结或加黑 |
| 正常完成是否恢复 | 不适用；下一统计周期恢复创建额度 |

## 9. 幂等、并发和审计

- 每个写操作要求 UUID `operation_id`；同一 ID 和相同请求返回第一次结果，同一 ID 携带不同请求返回冲突；
- 创建预约必须原子检查限制、停止新增时间和活动容量；
- 最后一个活动容量并发预约时只能有一个请求成功；
- 取消、失约和完成最多释放一次容量；
- 处罚事件必须与预约状态事实同事务写入，异步汇总失败不能丢失原始责任事件；
- 黑名单、限制、豁免和解禁必须版本化并产生业务审计；
- 项目、窗口、队列和报告管理写操作使用乐观版本；
- 主数据、状态历史、审计、幂等结果和 Outbox 保持本地事务一致。

## 10. 权限边界

患者只能操作已验证手机号对应的本人预约和报告。工作人员按照当前科室和 permission 操作：

- `appointment.read`：查看授权科室预约和队列；
- `appointment.update`：报到、排队、叫号、开始、完成和失约处理；
- `appointment.cancel`：医院原因取消；
- `appointment.catalog.manage`：维护检查项目、检查房间、房间—项目关系和前置条件；
- `appointment.capacity.manage`：维护房间开放配置、项目预约配置、停止新增时间和房间共享活动容量；
- `appointment.restriction.manage`：人工限制、豁免和解禁；
- Report 相关发布、更正、撤回、下载和导出沿用独立权限语义。

`super_admin` 可以跨科室管理，普通工作人员只能操作当前科室。权限通过不能绕过状态机、容量、限制版本
和报告版本。日志不得保存 Token、完整手机号、报告正文或不必要的患者信息。

## 11. 明确不进入当前简化范围

- 精确分钟预约和患者选择具体医生；
- 医生排班；
- 多项目总订单、独立 Planning Service、原子创建多条预约和自动修改已有预约；
- 独立改签事务；
- 支付、退款、医保和医生开单；
- 根据患者疾病、用药、年龄、性别、妊娠等个体条件自动判断检查适用性；
- 任意 DSL、动态 Evaluator、自由三元组或首期无法识别的新计算语义；
- 未经客户确认直接启用自动永久黑名单。

叫号和报告不在排除范围内，必须作为完整闭环继续设计和实施。
