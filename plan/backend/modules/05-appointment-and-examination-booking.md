# 预约检查服务

> 文档状态：业务讨论草案，预约时间粒度和资源归属方式待客户确认
>
> 上位文档：[业务能力全景](../overview/04-business-capability-map.md)、

## 1. 服务目标

Appointment Service 负责回答：某个就诊人选择的检查项目在什么院区、科室、地点和时间范围内可以
预约，确认时是否仍有容量，以及预约成功后如何取消、改签、报到和完成。

它是号源和容量的唯一事实源。Planning Service 可以生成检查组合和推荐顺序，但不能直接占用或释放
容量；Navigation Service 可以提供地点和路线耗时，但不决定一个检查是否可以预约。

当前项目讨论的是“检查预约”，不默认等同于患者选择具体医生的普通门诊挂号。

## 2. 首期需要完成的业务能力

首期至少需要覆盖：

1. 检查项目目录及其可预约状态；
2. 检查项目与院区、科室、地点之间的可执行关系；
3. 某一天或时间范围内的开放规则和容量；
4. 查询可预约日期、窗口或时段；
5. 为一个就诊人创建包含一个或多个检查项目的预约；
6. 确认时重新校验容量，并在同一事务内完成占用；
7. 取消预约并释放尚未使用的容量；
8. 记录待确认、已确认、已取消、已报到、检查中、已完成和失约等状态历史；
9. 使用 `operation_id` 防止重复请求造成重复预约或重复释放；
10. 保存预约发生时的检查项目、科室和地点必要快照。

首期不负责创建医学检查规则，不负责计算院内路线，也不把医生身份、科室主数据或地图地点复制为
本服务可以随意修改的主数据。

## 3. 数据与服务边界

Appointment 通过稳定 ID 引用其他领域：

| 引用 | 数据拥有者 | Appointment 的使用方式 |
|---|---|---|
| `patient_profile_id` | Patient 模块 | 标识预约属于哪个就诊人 |
| `department_id` | Identity Service | 标识业务科室，不能直接修改科室主数据 |
| `doctor_account_id` | Identity Service | 仅在确实按医生预约或后续分配医生时使用 |
| `location_id` | Navigation Service | 标识检查地点并查询路线，不复制地图结构 |

这些字段是跨服务逻辑引用，不建立跨数据库外键，也不通过跨库 JOIN 读取数据。创建可预约单元时，可以
通过 RPC 验证外部 ID；科室、医生或地点变化后，通过 Outbox/Kafka 事件更新本地可用状态。已经确认的
预约保留当时的名称和地点快照，不能因为主数据改名而篡改历史。

## 4. 当前存在争议的预约模型

### 4.1 方案 A：科室、检查项目、地点与精确时段绑定

示例：

```text
腹部超声
超声医学科
门诊楼二层超声室
2026-08-20 09:00～09:15
容量 2 人
```

患者选择或由系统推荐具体的小时间段。每个时段拥有明确容量，确认预约时占用该时段的容量。

优点：

- 患者到院时间明确；
- 多项检查之间可以进行较准确的冲突判断和顺序规划；
- 容量控制、迟到和失约边界比较明确；
- Planning 可以计算预计完成时间。

需要解决的问题：

- 医院是否真的按十五分钟、三十分钟等粒度运营；
- 不同患者的检查耗时是否足够稳定；
- 设备故障、医生延迟和现场插队如何处理；
- 小时段数量较多，排班维护和号源生成更复杂。

方案 A 不要求一定选择医生。容量可以绑定“检查项目 + 科室 + 地点”，由科室内部安排实际执行人员。

### 4.2 方案 B：时间与具体医生绑定

示例：

```text
张医生
腹部超声
2026-08-20 09:00～09:15
容量 1 人
```

该方案把医生作为主要可预约资源，患者预约时确定具体医生和时段。

优点：

- 适合必须由指定医生完成的门诊或检查；
- 医生工作量和排班关系清晰；
- 患者能够主动选择医生。

主要风险：

- 医生调岗、请假、替班会直接影响已有预约；
- 检查容量可能实际受设备和检查室限制，而不是只受医生限制；
- 需要完整的医生排班、停诊、替诊和预约迁移规则；
- 当前产品主线是检查预约，尚未确认患者是否需要选择具体医生。

除非客户明确要求“患者必须选择医生”，首期不建议采用方案 B。Identity 仍只保存医生身份和所属科室，
医生排班即使未来实现，也必须放在 Appointment Service。

### 4.3 方案 C：科室、检查项目、地点与大时间窗口绑定

示例：

```text
腹部超声
超声医学科
门诊楼二层超声室
2026-08-20 上午 09:00～12:00
窗口容量 60 人
```

患者预约某一天、上午、下午或全天开放窗口，不获得精确到分钟的检查时间。患者在窗口内到达，报到后
按照医院现场规则排队。

优点：

- 更接近部分医院“预约日期或时段、现场排队”的实际流程；
- 不依赖具体医生排班；
- 规则和维护成本明显低于精确小时段；
- 仍可通过窗口容量避免同一天无限预约。

需要解决的问题：

- 窗口总容量由谁制定，是否区分上午和下午；
- 最晚报到时间、过号、迟到和失约如何处理；
- 是否已有叫号系统，能否取得实时排队进度；
- 同一窗口内的患者按照预约顺序、报到顺序还是人工优先级处理；
- 没有实时队列数据时，只能给出建议顺序，不能承诺准确完成时间。

如果方案 C 完全不限制人数，它就只是登记意向，不是可控的预约。因此即使没有小时间段，也必须设置
日期或窗口容量。

## 5. 三种方案对比

| 对比项 | 方案 A：精确时段 | 方案 B：医生时段 | 方案 C：大时间窗口 |
|---|---|---|---|
| 患者获得的承诺 | 具体检查时段 | 具体医生和时段 | 某天或上午/下午可到院 |
| 容量主要绑定 | 项目、科室、地点、时段 | 医生、项目、时段 | 项目、科室、地点、窗口 |
| 是否需要医生排班 | 否 | 是 | 否 |
| Planning 精度 | 较高 | 较高 | 只能估算和动态建议 |
| 现场排队依赖 | 中 | 低到中 | 高 |
| 首期复杂度 | 中 | 高 | 低到中 |
| 后续扩展成本 | 可继续细化资源 | 需要完整人员排班体系 | 可逐步拆分为精确时段 |

## 6. 推荐的兼容模型

首期建议采用“可预约单元 + 可用窗口”，不要把数据库直接锁死为某一种粒度：

```text
booking_unit
  = 检查项目 + 院区/科室 + 检查地点

availability_window
  = 某个 booking_unit 在某天的开始时间、结束时间和容量
```

窗口可以同时表达：

```text
方案 A：09:00～09:15，容量 2
方案 C：09:00～12:00，容量 60
```

概念字段可以包括：

```text
appointment_booking_units
  booking_unit_id
  exam_item_id
  department_id
  location_id
  booking_mode       fixed_slot | arrival_window
  status

appointment_availability_windows
  window_id
  booking_unit_id
  service_date
  start_at
  end_at
  total_capacity
  reserved_capacity
  status
  version
```

医生不是首期必填字段。预约项目可以保留可空的 `doctor_account_id`，在客户确认按医生预约或医院后续
分配执行医生时再使用。不能为了可能出现的医生排班，提前把排班字段加入 Identity 医生表。

当前倾向为：首版采用方案 C 的“上午/下午窗口 + 明确容量”，底层使用上述通用窗口模型；客户确认需要
精确预约后，再把部分可预约单元配置为方案 A。方案 B 暂缓。

## 7. 与 Planning 和 Navigation 的协作

Appointment 向 Planning 提供候选窗口、容量状态、检查地点和项目 ID。Planning 先排除医学规则、时间
范围和移动时间上不可行的组合，再生成一个或多个候选方案。

Navigation 只负责返回地点之间的距离、路线和预计移动时间。Planning 综合以下信息进行评分：

```text
检查先后硬约束
+ 预约窗口或精确时段
+ 预计检查耗时
+ 等待时间
+ 地点间移动时间
+ 用户偏好
```

方案 A 可以生成相对准确的时间安排；方案 C 只能生成“建议先后顺序 + 预计移动时间”，实际等待时间
取决于现场队列。用户选择候选方案后，Appointment 必须重新校验所有容量，并按照“全部成功或全部
失败”的原则原子确认；Planning 和 Navigation 都不能代替这次最终校验。

## 8. 需要客户确认的争议项

在设计最终状态机和建表迁移前，至少确认：

1. 预约成功后，医院承诺具体检查时间，还是只承诺日期、上午或下午可以到院；
2. 患者是否需要选择具体医生，还是由科室在现场安排；
3. 容量实际受科室总量、检查项目、设备、检查室还是医生限制；
4. 大时间窗口是否设置人数上限，上限由谁维护；
5. 到院后是否已有报到和叫号系统，能否与本系统同步；
6. 现场按照预约顺序还是报到顺序叫号，是否存在急诊或人工优先级；
7. 多项检查必须全部预约成功，还是允许部分项目成功；
8. 是否允许患者取消和改签，距离开始时间多近时禁止操作；
9. 设备故障、科室停诊或地点关闭后，已有预约是自动改签、重新规划还是人工处理；
10. 首期是否只支持一个院区、少量检查项目和模拟容量，还是直接接入医院真实号源。

## 9. 当前建议的首期范围

在客户尚未确认精确排班前，建议首期限定为：

- 选择一个就诊人和一个或多个检查项目；
- 按“检查项目 + 科室 + 地点”建立可预约单元；
- 提供上午/下午开放窗口和明确容量；
- 不允许患者选择具体医生；
- 多项目预约全部成功或全部失败；
- 支持容量占用、取消释放、幂等和并发测试；
- 支持预约、报到、完成、取消和失约的基础状态历史；
- Planning 返回推荐顺序，不承诺窗口内的精确执行时间；
- 为未来细分精确时段、增加设备资源和医生排班保留扩展位置。

客户确认方案 A、B 或 C 后，再补充正式状态机、容量计算规则、错误码、RPC/HTTP 契约和数据库迁移。
