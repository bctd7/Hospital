# Appointment 当前范围已实现归档

## 业务边界

Appointment 围绕一次检查预约提供两组业务入口：患者创建和管理本人预约，工作人员管理科室资源、处理检查
并编写报告。医生是授权操作者，不是预约资源，也不参与窗口和容量模型。

## 检查资源

- 一个检查项目只属于一个科室；
- 一个房间只属于一个科室，并严格保存院区、楼栋、楼层和房间号；
- 同一科室内，房间与检查项目可以多对多关联；
- 管理端按“科室 -> 房间 -> 可执行项目”维护，患者端按“科室 -> 项目 -> 房间”选择；
- 房间退役只作为后端状态保护，当前小程序不展示停用资源开关或恢复入口。

房间周窗口与项目周窗口是两条独立配置：

- 房间窗口定义星期、上午/下午、开放起止时间和该房间共享容量；
- 项目窗口定义星期、上午/下午、预约开始、停止新增和结束时间；
- 上午以 12:00 为边界，下午从 12:00 之后开始；
- 项目窗口必须完整落在关联房间同星期、同大窗的开放窗口内；
- 同一房间同一日期和大窗的所有项目共用容量，每条预约占一个单位。

每个检查项目还保存预计检查时长，创建时必填，范围为 5～480 分钟且必须是 5 分钟的整数倍。该时长用于患者
预期展示和后续智能导诊估算，不是实际执行倒计时，也不改变“一条预约占一个容量单位”的规则。

## 预约

患者只能预约当前自然周且尚未超过项目停止新增时间的选项。创建预约时在同一 MySQL 事务内：

1. 消耗患者当周额度；
2. 建立“患者 + 项目 + 具体日期 + 上午/下午”唯一活动占用；
3. 锁定并扣减“房间 + 具体日期 + 上午/下午”容量；
4. 保存项目、房间、地址、时间窗口和预计检查时长快照；
5. 记录幂等结果。

每名患者每自然周最多成功预约 10 次。取消、完成和未到场都不返还当周额度。患者可以在同一具体日期和同一
上午/下午预约多个不同项目；同一项目只能存在一条待检查或检查中的预约，换房间不能绕过该限制。项目完成、
预约取消或标记未到场后释放占用，可以再次预约同一项目、同一日期和大窗，并重新消耗一份周额度。

项目预计时长后续修改只影响新预约；既有预约、消息和预约列表继续读取预约创建时保存的时长快照，避免患者
已经确认的预计用时被后台配置修改。该快照不等于精确预约时间片。

## 状态机

```text
confirmed（待检查）
  -> in_progress（检查中）
  -> completed（已完成）

confirmed -> no_show（未到场）
confirmed -> canceled（已取消）
```

- 不设置独立“已到院”状态；工作人员在项目时间范围内直接开始检查；
- 到达项目最晚结束时间仍为 `confirmed` 的预约，由后台任务标记为 `no_show`；
- `in_progress` 不会因为时间到达而自动完成，避免医生尚未写完报告时丢失编辑能力；
- 超过项目结束时间后不能再把 `confirmed` 改为 `in_progress`；
- 配置关闭或容量降低会在事务内处理受影响的待检查预约，已开始检查会阻止破坏性配置变化。

诊前列表只显示 `confirmed` 和 `in_progress`；诊后记录显示 `completed` 和 `no_show`。`canceled` 保留为消息、
幂等和审计事实，不进入普通预约列表。对用户界面而言终态不可逆，后台仍保留数据库状态事实。

## 检查报告

- 每个检查项目可以配置统一报告模板；
- 一次预约最多对应一个报告主体；
- 只有本科室授权工作人员可以保存草稿、完成并发布或发起更正；
- 完成检查、发布首版正式报告和释放容量在同一事务内提交；
- 正式报告不能覆盖修改，更正会新增不可变版本并保留原版；
- 患者只读取本人当前有效正式版本；工作人员按科室查看检查记录、草稿和版本历史；
- 执行人员来自实际开始检查的账号及当时展示昵称快照，不在前端写死。

报告字段当前包括客观所见、检查结论、建议和备注；报告保存预约时的项目、科室、房间、地址、患者和执行
人员快照，后续基础资料变化不会改写已形成的医疗记录。

## 消息

患者消息包括预约成功、到院前 60 分钟、到院前 30 分钟、报告发布和报告更正。工作人员消息按科室包括
新预约、取消、未到场、报告到期和报告超时。

消息正文从预约和报告事实动态生成，数据库只额外保存“账号 + 消息键”的已读时间。因此同一科室消息可被
多名医生分别标记已读，又不会复制医疗正文。消息跳转复用已有预约或报告页面。

## 代码结构

```text
service/appointment/rpc/internal/
├─ manager/
│  ├─ shared/     患者与工作人员共用读取
│  ├─ patient/    本人预约、报告和消息
│  ├─ staff/      科室资源、预约、检查、报告和消息
│  └─ common/     领域数据、错误、缓存与事务端口
├─ repository/mysqlstore/
├─ logic/
└─ svc/
```

第一层按使用者划分，不再使用含义重叠的 `catalog`、`resource` Manager。项目、房间、排期、预约和报告模型
均留在对应 Manager 业务边界内，没有额外创建独立 Report 服务。

## 缓存与防超卖

- 资源热点缓存 5 分钟并增加随机抖动；预约候选使用 20 秒短缓存；
- 同实例合并相同缓存键并发回源；
- 写后递增科室 generation，不扫描删除大量旧键；
- Redis 失败回源 MySQL；
- 容量、患者时段、额度和状态机始终由 MySQL 事务与锁裁决。

因此缓存只影响读取性能和短时展示，不授予预约资格，也不会造成超卖。

## 当前不包含

- 医生排班、医生选择或医生容量；
- 跨周预约和复杂时间片；
- 节假日特殊规则；
- 自动选择最优科室或房间；
- 对象存储影像、缴费、医保和票据。
