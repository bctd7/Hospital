# Appointment 当前范围已实现归档

## 业务边界

Appointment 拥有检查项目、房间、周窗口、预约容量、患者检查报到、房间候检队列、检查执行、报告和消息事实。
Identity 只提供账号、院区、科室和授权上下文；医生是授权操作者，不是预约资源，也不参与窗口或容量模型。

## 检查资源与预约

- 一个项目只属于一个科室，一个房间也只属于一个科室；
- 房间严格保存院区、楼栋、楼层和房间号，同一科室内房间与项目可以多对多关联；
- 房间周窗口保存开放起止时间与共享容量，项目周窗口独立保存开始、停止新增和结束时间；
- 项目窗口必须完整落在关联房间同星期、同大窗的开放窗口内；
- 同一房间、具体日期和上午/下午的所有项目共用容量，每条活动预约占一个单位；
- 项目预计时长按 5 分钟递增，只用于页面展示和后续智能规划，不控制现场检查。

患者只能预约当前自然周，每周最多成功预约 10 次，取消、未到场和完成都不返还额度。同一患者可以在同一日期
和大窗预约多个不同项目；同一项目在 `confirmed`、`queued`、`called` 或 `in_progress` 时不能换房间重复预约。
进入 `report_pending`、完成、取消或未到场后释放该唯一占用，可以再次预约并重新消耗额度。

预约创建在一个 MySQL 事务内消耗周额度、声明患者项目占用、锁定日期容量、保存项目/房间/地址/时间/预计时长
快照并记录幂等结果。缓存只加速读取，不参与容量和资格裁决。

智能预约确认复用同一组事务规则，并由批量命令在一个 MySQL 事务内创建整组预约；任一项目的额度、重复占用、
窗口或共享容量校验失败时整组都不落库。重复确认同一个 Guidance 方案返回首次创建的预约 ID，不重复占用容量。

项目创建和项目基本事实更新不再提供可绕过规则配置的公开 HTTP 写入口。Guidance 是完整项目配置协调者，Appointment
只保存自身项目事实和不可见的 TCC 预提交记录；Guidance 确认规则落库后才最后确认 Appointment 项目，失败则幂等
取消。房间关联、项目周窗口、容量和报告模板仍由 Appointment 资源管理独立维护，不进入该分布式事务。

## 检查报到与房间队列

```text
confirmed（待报到）
  -> queued（排队中）
  -> called（正在叫号）
      -> queued（叫号一分钟超时，顺延三次实际叫号）
      -> in_progress（工作人员确认患者到场并开始检查）
  -> report_pending（实际检查结束，报告待完成）
  -> completed（正式报告已发布）

confirmed -> no_show（停止新增时间仍未报到）
called    -> no_show（项目结束后叫号超时）
confirmed -> canceled（报到前取消）
```

- 患者从项目开始至停止新增时间主动报到，工作人员不能代替；报到后不能取消；
- 队列范围是“房间 + 具体日期 + 上午/下午”，同房间不同项目共享队列；
- 候检号单调递增且不回收，过号通过最早可再次叫号轮次顺延，不移动整条队列；
- 后面无人时忽略未完成的三次顺延，避免唯一患者永久卡住；
- 多人都处于顺延期时，兜底按最早恢复叫号资格的轮次、再按候检号选择，避免较小候检号反复超时后挤占后续患者；
- 较早大窗遗留队列优先；项目结束后已报到的患者仍可继续叫号和检查；
- 每个房间任何时刻只允许一个现场处理占位，即 `called` 或 `in_progress` 二选一；开始检查前必须先由系统叫号；
- 结束实际检查立即释放容量和患者项目占用并进入 `report_pending`，不等待报告发布；
- 后台任务每批加锁处理停止报到后的 `confirmed` 及叫号超时，缓存按科室 generation 失效。

现实广播是正式叫号渠道，小程序消息只作辅助。第一版不预测等待分钟、不支持人工插队、急诊权重或设备故障调度。

## 检查报告

- 项目可以配置统一报告模板；一次预约最多一个报告主体；
- `in_progress` 和 `report_pending` 均可保存草稿；只有 `report_pending` 可以发布首版正式报告；
- 发布只把预约变为 `completed`，不会重复释放已在结束检查时释放的资源；
- 科室预约页结束检查后直接进入报告编辑详情；暂不填写时可返回，之后从检查记录继续处理 `report_pending`；
- 正式报告不可覆盖，更正会新增不可变版本并保留原版；
- 患者只读取本人已发布报告，工作人员按授权科室读取草稿、报告和版本历史；
- 执行人员来自实际开始检查的账号昵称快照，结束人员和发布人员分别保存自己的快照。

## 消息

患者消息包括预约成功、报到截止前 60/30 分钟、正在叫号、过号顺延、未到场、报告发布和报告更正。工作人员
消息按科室包括新预约、取消、未到场、报告到期和报告超时。队列事件以追加事实保存；其他正文从预约和报告事实
动态形成。数据库只额外保存每个账号自己的消息已读时间。

## 代码结构

```text
service/appointment/rpc/internal/
├─ manager/
│  ├─ shared/     患者与工作人员共用读取
│  ├─ patient/    本人预约、报到、报告和消息
│  ├─ staff/      科室资源、叫号、检查、报告和消息
│  └─ common/     领域模型、错误、缓存和窄事务端口
├─ repository/mysqlstore/
├─ logic/
└─ svc/
```

队列没有建立新的平行业务包：患者动作留在 `manager/patient`，工作人员动作留在 `manager/staff`，MySQL 实现
留在现有 repository。`QueueTxStore` 是队列写入使用的窄事务端口，不污染项目配置事务。

## 数据、缓存与验证

初始迁移为 `migrations/appointment/000001_appointment_initial_schema`，其中队列主体、成员和
事件分别是 `appointment_check_queues`、`appointment_check_queue_entries` 和
`appointment_check_queue_events`，项目配置参与记录为
`appointment_examination_item_configuration_transactions`。契约事实源是 `contracts/api/appointment-*.api` 与
`contracts/proto/appointment/v1/appointment.proto`。

- 资源热点缓存 5 分钟并带随机抖动，预约候选使用 20 秒短缓存；
- 相同缓存键并发回源在单实例合并，Redis 失败时回源 MySQL；
- 所有报到、候检号、叫号轮次、超时、容量、唯一占用和状态迁移均由 MySQL 事务裁决；
- 综合测试数据包含 31 条预约，覆盖八种预约状态、四个科室今日数据、五个共享队列、窗口内顺延与窗口后未到场
  两个叫号超时对照案例，以及空白待写、
  草稿、正式报告和更正版本；真实超级管理员账号继续复用原有身份，不生成同手机号重复患者。

## 当前不包含

- 医生排班、医生选择或医生容量；
- 跨周预约、细粒度时间片和节假日特殊规则；
- 人工插队、过号人工恢复、预计等待时长和队列驱动的智能导航；
- 对象存储影像、缴费、医保和票据。
