# Appointment 组织只读副本提案

> 状态：仅保留为后续优化提案，当前未实施，也不是现有 Appointment 功能的前置条件。

## 当前方式

院区、科室和医生由 Identity 拥有，检查项目和房间由 Appointment 拥有。小程序页面需要同时展示两类数据时，
App API 或前端服务层分别查询后按稳定 ID 组合。这个边界正确，但页面查询数量会随资源树继续增长。

## 可选优化

Identity 在组织变化事务中写 Outbox，Kafka 传递组织事件；Appointment 消费后维护只读组织副本，用于返回
“院区 -> 科室 -> 房间 -> 项目”的页面读模型。

```text
Identity 主数据 + Outbox
  -> Kafka
  -> Appointment 组织事件 Consumer
  -> Appointment 只读组织副本
  -> 页面聚合查询
```

副本只能用于展示和查询，不能成为组织写入入口，也不能绕过 Identity 权限。事件需要包含版本并保证单调、
幂等；出现延迟时，Appointment 业务写入仍以 Token 中的稳定 `department_id` 和自己的资源规则为准。

## 何时实施

只有在真实监控证明跨服务页面聚合成为性能或维护瓶颈，并且组织变更事件的版本、重放和重建方案完成评审后
再实施。当前数据量和调用链不需要为了“看起来解耦”提前增加这套基础设施。
