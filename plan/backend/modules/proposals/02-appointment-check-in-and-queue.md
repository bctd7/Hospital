# Appointment 检查报到与候检叫号实施计划

> 状态：业务规则已确认，尚未实施。本文只规划 Appointment 扩展，不把候检人数或预计等待时间接入第一版
> 智能导诊。

## 目标与边界

在现有预约和报告之间补齐现实检查现场的报到、候检、叫号、开始检查、结束检查和待报告过程。Appointment
继续拥有预约状态、房间队列、容量、报告和消息事实；Identity 不增加相关表或接口。

第一版不实现急诊插队、设备故障调度、人工权重、等待时间预测、微信后台推送或候检队列驱动的智能导航。
现实广播仍是正式叫号渠道，小程序只同步状态并提供辅助提醒。

## 状态机

```text
confirmed（待到场）
  -> queued（排队中）
  -> called（正在叫号）
      -> queued（叫号超时，顺延三次叫号）
      -> in_progress（医生确认患者到场并开始检查）
  -> report_pending（实际检查结束，报告待完成）
  -> completed（正式报告已发布）

confirmed -> no_show（停止新增时间仍未报到）
called    -> no_show（最晚结束时间后叫号超时）
```

- 患者只能把自己的 `confirmed` 预约变为 `queued`，医生不能代替患者报到；
- 医生只能对系统选出的 `called` 患者开始检查；
- 同一房间不能同时存在多个 `called`，也不能同时执行多个 `in_progress`；
- 医生结束实际检查时进入 `report_pending`，不能等待报告发布才释放房间；
- 患者报到后不能取消、主动退出队列或放弃正在叫号；
- `queued`、`called` 和 `in_progress` 继续占用预约资源；`report_pending` 立即释放房间容量和同项目重复预约占用；
- `report_pending` 允许继续保存报告草稿，发布报告后才进入 `completed`。

## 时间规则

项目窗口的三个时间保持独立：

- 开始时间：开放患者报到和医生叫号；
- 停止新增时间：同时停止新增预约和患者报到，仍未报到的预约立即变为 `no_show`；
- 最晚结束时间：约束正常计划时间，不错误处罚已经报到但尚未叫到的患者。

最晚结束时间后，已报到队列继续叫号并允许开始检查，直到队列清空。此时被叫患者一分钟内没有开始检查，
直接标记为 `no_show`，不再顺延。预计检查时长不参与现场倒计时、自动结束或叫号，只继续服务预约展示和后续
智能规划。

## 队列边界与顺序

队列唯一范围是“房间 + 具体日期 + 上午/下午”。同一房间的不同检查项目共用队列，不同房间各自排队。
患者报到后取得该范围内单调递增且不回收的候检号。

正常情况下按候检号从小到大叫号。正在叫号持续一分钟；超时后患者恢复为 `queued`，至少经过后续三次实际
叫号才重新取得资格，这三个人不要求成功开始检查。后面没有其他符合条件的患者时，不等待不存在的三个人，
允许重新叫该患者。

同一房间较早大窗的队列延迟到下一大窗时，较早队列优先清空；后一大窗患者可以报到，但必须等待。第一版不
提供工作人员手工跳过整个遗留大窗或任意调整队列顺序。

## 推荐的数据事实

实施前先用数据库集成测试验证以下关系模型，再写正式 Migration：

1. 队列主体：房间、服务日期、大窗、下一个候检号、当前叫号轮次、当前叫号预约和并发版本；
2. 队列成员：预约、候检号、最早可再次叫号轮次、叫号次数、报到时间、叫号时间和叫号截止时间；
3. 队列事件：报到、叫号、超时顺延、开始检查和结束检查的追加事实，用于审计和现有消息页。

优先验证“候检号 + 叫号轮次”，过号只更新当前成员和队列轮次，不移动其他患者。若最终选择链式结构，必须
额外证明并发报到、移动节点、超时任务和故障恢复不会产生断链、环或死锁；未通过这些测试前不得实施链表。
预约状态仍是业务状态唯一来源，队列成员不再维护另一套相互冲突的状态机。

## Manager 与事务职责

所有动作继续下降到 `service/appointment/rpc/internal/manager/patient` 或 `manager/staff`，公共状态、错误和窄
Store 端口留在 `manager/common`，MySQL 实现在现有 `repository/mysqlstore`，不新建平行业务目录。

- 患者报到：锁预约和队列，校验本人、状态与时间，分配候检号并写事件；
- 叫下一位：锁房间当天相关队列，先处理较早大窗，选择最早有资格成员，建立一分钟截止时间并写事件；
- 开始检查：只允许当前 `called` 预约，清除当前叫号占用并进入 `in_progress`；
- 结束检查：进入 `report_pending`，释放容量与重复预约占用并允许房间继续叫号；
- 发布报告：只负责从 `report_pending` 进入 `completed`，不再次释放已经释放的资源；
- 后台清理：批量处理停止新增时仍未报到的预约及叫号超时，使用数据库时间、行锁、跳锁和有限批次；
- 所有患者和工作人员写操作保持操作 ID 幂等，自动任务使用稳定事件键防止重复顺延或重复消息。

缓存只能服务队列和页面读取。候检号分配、当前叫号、超时顺延、状态迁移和资源释放必须以 MySQL 事务为准，
不能使用 Redis 锁或缓存计数作为正确性来源。

## 接口与消息计划

契约阶段补充以下能力，具体字段只维护在 `contracts/api` 和生成的 gRPC 契约中：

- 患者对本人预约执行检查报到；
- 患者读取本人候检号、当前叫号和前方人数；
- 工作人员按本科室、日期和房间读取队列；
- 工作人员叫下一位、开始检查和结束检查；
- 现有预约与检查记录接口识别新增状态；
- 现有消息接口增加正在叫号和过号顺延事件。

叫号消息包含项目、科室、严格房间地址、候检号和一分钟提示；顺延消息说明已经过号并将在后续三次叫号后重新
进入可叫范围。消息页是辅助记录，不增加独立入口，也不把通知授权作为报到条件。

## 小程序改动

患者端继续复用“我的预约”“检查记录”和“消息”：

- 待到场在项目开始至停止新增之间展示检查报到；
- 排队中展示候检号、当前叫号和前方人数，不显示预计等待分钟；
- 正在叫号突出严格房间地址和一分钟倒计时；
- 检查中展示执行状态；
- 报告待完成移入检查记录并展示“报告生成中”，发布后展示查看报告。

工作人员端继续复用“科室预约”：

- 默认今天、本科室，顶部切换房间；其他日期只读，每次进入恢复今天；
- 房间顶部只有一个互斥状态面板：当前空闲、正在叫号或正在检查；
- 当前面板下方展示按上一大窗遗留、当前大窗分组的候检列表；
- 房间空闲时提供叫下一位，正在叫号时提供开始检查，正在检查时提供结束检查；
- 结束检查后的预约进入现有待完成报告流程。

项目窗口编辑把开始、停止新增和最晚结束全部改为按五分钟递增的时间选择器，不保留 `HH:MM` 手工输入框。

## 实施阶段

1. **契约和状态评审**：固定状态名、时间边界、错误码、权限和页面映射；更新 API 源文件但不接 UI；
2. **数据库与 Manager**：压平 Appointment 最新 Migration，完成队列事务、状态迁移、超时任务和资源释放；
3. **后端协议适配**：补齐 gRPC、App API、消息读取和缓存失效，验证所有端口预期返回；
4. **患者端**：接入报到、候检展示、叫号倒计时、检查记录和消息；
5. **工作人员端**：接入今日房间队列、叫下一位、开始检查、结束检查和待报告；
6. **回归与数据**：重建空数据库，生成覆盖所有状态的综合数据，完成并发集成测试、全仓检查和开发/正式包构建；
7. **归档**：验收后把稳定规则合并进 Appointment 已实现文档，删除重复或过期提案说明。

每一阶段通过测试后再进入下一阶段，不能同时改状态机、队列算法和两个前端页面后再统一排错。

## 验收重点

- 开始时间前不能报到或叫号，停止新增时间后未报到预约准确转为未到场；
- 同一房间并发叫下一位只有一个成功，同一预约并发报到只分配一个候检号；
- 过号准确顺延三次实际叫号，后面无人时不会永久卡住；
- 较早大窗遗留队列优先，最晚结束后已报到患者仍能完成检查；
- 检查中未结束时不能叫下一位，结束检查立即释放资源且不依赖报告发布；
- 报告待完成可以继续保存和发布，发布过程不重复释放容量；
- 患者只能操作本人，工作人员只能操作授权科室，越权统一拒绝；
- 患者与工作人员页面不新增一级入口，状态、按钮和消息与后端事实一致；
- 智能导诊不读取候检人数，也不产生等待时间预测。
