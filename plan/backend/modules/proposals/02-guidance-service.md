# Guidance 智能导诊业务逻辑

> 状态：第一版主流程已经实现；检查项目完整配置、智能预约、整组原子预约、当日顺序建议和地图导入均已接入。
> 本文重点回答 Guidance 已经完成哪些业务功能、
> 功能之间如何衔接，以及它与 Appointment、Identity 和地图能力如何分工。

## 一、业务目标

Guidance 是独立服务，负责把“检查顺序、预约组合和地图路线”串成一条连续的患者旅程。它不取代 Appointment：

- Guidance 回答“这些检查怎样组合、按什么顺序完成、下一站去哪里”；
- Appointment 回答“项目能否预约、房间是否有容量、患者当前处于什么检查状态”。

面向患者时，Guidance 分为两个相互衔接但职责不同的阶段：预约前的**智能预约**和预约后的**当日检查路线**。
两者共用同一套检查规则、地点资料和路线计算能力，但不会把预约规划和现场导航混成一个页面。

## 二、两块患者能力

### 2.1 智能预约：在预约前形成可执行方案

患者选择多个检查项目和若干可到院日期后，Guidance 按以下顺序形成少量预约方案：

1. **先满足专业顺序。** 如果工作人员已经配置某项检查应先于另一项检查，候选方案必须遵守该顺序。
2. **再协调检查准备状态。** 需要空腹的检查尽量在进食前集中完成；共享其他准备要求的检查也尽量连续安排，
   等相关检查全部完成后再提示患者解除准备状态，避免反复准备。
3. **再满足可预约窗口。** 每个项目只确定预约日期、上午或下午大窗和可执行房间，不虚构大窗内的精确到院时刻；
   同一窗口内的实际执行顺序留给当天导航和现场流程决定。
4. **最后优化空间路线。** 对不存在顺序和准备冲突的项目，优先把同一院区、同一楼栋的检查安排在一起，再比较
   不同组合的移动成本。

地图在这一阶段属于规划依据，而不是患者正在执行的导航。系统可以在后台比较不同楼栋之间的距离和耗时，但方案
只需要说明必要的先后关系、可以自由调整的检查集合、预约大窗、楼栋组合和选择理由，不展开完整路线图，也不把
所有项目强行排成一条固定序列。患者选定方案后，Appointment 对整组预约执行最终校验和创建。

智能预约方案保存的是“顺序骨架”，而不是一张精确日程表。顺序骨架包括本次方案命中的必要依赖、准备阶段及其
先后关系；这些内容随已选方案保留，检查当天不能重新推翻。骨架内部没有约束的部分不保存固定顺序，由当天导航
重新计算。

例如 A 必须先于 B，而 C 与两者都没有关系时，只保存 `A -> B`，不会为了形成列表而额外规定 C 的位置。检查开始时
A 和 C 都可以成为下一站；A 完成后 B 也进入可选集合，不要求必须先完成 C。又如两项检查都要求空腹，则可以保存
“空腹检查集合 -> 后续检查集合”的阶段关系；空腹检查集合内部谁先做仍由当天决定，最后一项完成后再提示患者
禁食限制已经结束。

第一版已经具备“检查项目直接先后关系”以及带弹性时间范围的禁食、禁水和喝水准备状态。
三者都从规划器推导出的时点持续到对应检查完成，不统一绑定上午或下午窗口的开始时间。系统不单独保存“恢复
饮食”，最后一项相关检查完成后，禁食状态自然结束。提前用药、服用泻药、怀孕或可能怀孕等内容作为患者提醒，
不参与排序，也不成为预约的强制准入条件。

### 2.2 当日检查路线：根据真实进度指导下一站

预约创建以后，当日检查路线读取患者当天的普通预约和 Appointment 实时状态，不再重新创建预约：

1. 如果检查之间存在明确顺序，就先执行当前已经满足前置条件的项目；没有关系的项目同时进入可选集合；
2. 对没有明确顺序的剩余检查，系统可以根据楼栋集中程度、实际移动路线和可靠的现场运行信息重新比较先后；
3. 已完成、检查中、正在叫号、候检、未报到、取消和未到场等状态会持续缩小“尚待完成”的范围；
4. 系统选择下一站后，调用统一的两点路线能力，把“当前位置或上一站 -> 下一站”真实绘制在微信地图中；
5. 后台可以随着预约状态和现场工作量重新计算当前推荐，但不为“发现更优方案”发送消息、弹窗或更新提示；患者
   主动打开推荐页面时读取当前最新结果。

这里的“实时调整”只能调整仍可自由排序的剩余检查，不能违反专业顺序、项目窗口或 Appointment 已经进入的现场
流程。队列可以成为未来的相对参考，但人数少并不等于等待时间短；在缺少可靠检查速度模型时，不能把队列人数
直接换算成精确等待分钟，也不能宣称得到了物理世界中的绝对最优路线。

### 2.3 两个阶段如何串联

智能预约输出的是“预约日期、大窗、房间以及顺序骨架”，当日检查路线接收的是“已经创建的预约、已保存的骨架与
当前执行状态”。两者通过同一份方案和预约事实衔接：

- 智能预约保存必要依赖和准备阶段，标明哪些项目可以自由调整，但不生成精确时刻表，也不展示完整路线；
- Appointment 创建并维护每一条预约；
- 到检查当天，Guidance 保留顺序骨架，只从所有已满足前置条件、仍处于可执行窗口的项目中重新选择下一站；
- 每次确定下一站后，再调用地图能力展示实际行走路线。

当日推荐只是可选方案。患者先选择某个推荐方案，随后明确确认是否将它导入地图；只有确认导入后，才要求患者通过
地点搜索填写本次路线的院外初始出发地址，并把“院外初始地址 -> 第一站 -> 后续站点”交给地图形成路线说明。
第一段属于到院路线，需要按患者交通方式到达第一项检查所在楼栋；进入医院后，后续楼栋之间属于院内步行路线。
拒绝导入时继续查看方案，不提前获取地址。这个操作不修改预约、不执行报到，也不强制患者按顺序完成。第一段以后
直接使用上一检查站作为下一段起点，不重复询问出发地址。

第一段交通方式只支持公共交通、驾车和步行。驾车表示路线计算，不扩展为打车、叫车、费用或车辆订单业务；院内
阶段统一使用步行。

后台后续重新计算时静默更新推荐数据，不发送任何“发现更好方案”通知，不用推荐变化打断患者当前正在查看的地图
路线。患者再次主动进入推荐页面时自然看到最新结果。

地图路线按相邻站点拆成多个阶段，例如“当前位置 -> A”“A -> B”“B -> C”。小程序可以列出全部阶段和说明，
默认只突出当前阶段；患者点击其他阶段只是在地图上预览对应的 A 到 B 路线，不改变推荐、预约或检查状态。每一段
继续复用已经实现的两点路线能力，不把多站方案塞进两点路线接口。

“导入地图”只在小程序本机保存当天路线快照，不写入 Guidance MySQL 或 Redis，也不成为跨设备同步的业务事实。
服务端仍只根据 Appointment 事实计算推荐和路线；本地快照用于患者退出页面后恢复当前地图，不影响后台推荐结果。

这样，地图不是一个孤立功能：预约前用于比较方案，预约后用于执行方案；同一项两点路线能力可以被规划器反复调用，
也可以直接把最终路线交给患者查看。

## 三、完整业务闭环

```text
工作人员创建项目并完成顺序规则、准备规则和患者提醒配置
  -> 患者选择检查项目、可到院日期和偏好
  -> Guidance 读取项目、房间、窗口、号源和地点事实
  -> 排除不可行组合
  -> 按医学顺序、准备状态、时间和空间形成检查组
  -> 生成不超过三个可解释方案
  -> 患者选择并一次确认整套方案
  -> Appointment 原子创建全部预约
  -> Guidance 从普通预约生成检查导航
  -> Appointment 状态变化推动下一站更新
```

其中任何推荐都不能绕过 Appointment 的容量、重复预约、每周额度、时间窗口和状态机校验。

## 四、维护检查项目规则

### 工作人员配置闭环

工作人员端采用连续三步，不再把项目创建、规则配置和房间关联拆成互不相干的入口：

1. **新建检查项目。** 填写名称、所属科室、预计时长等 Appointment 项目事实；项目仍由 Appointment 保存和拥有，
   不再把通用 `description` 当作项目简介；
2. **配置前后关系。** 维护本项目与已有项目之间的直接先后关系，也允许明确确认“没有前后关系”；
3. **智能解析准备要求。** 在 `description` 中输入或粘贴客户提供的自然语言规则说明，整理为禁食、禁水、喝水和
   患者提醒，工作人员检查解析结果后确认保存。

房间资源页只允许把已经存在的检查项目关联为该房间的可执行项目，不能在房间后面直接创建新项目。这样每个新
项目都会经过规则配置流程，但“没有先后关系、没有准备规则、没有额外提醒”本身也是合法且需要明确确认的结果。

该流程只是前端把两个服务的能力串联起来，不改变数据归属：项目基本事实和房间关系仍属于 Appointment；自然语言
规则说明 `description`、项目先后关系、准备规则和患者提醒属于 Guidance。服务之间需要项目事实时通过后端契约
读取，不通过前端拼接成服务间通信，也不跨库读取。

三步配置采用一次性分布式事务，不允许第一步完成后就产生一个可见的半成品项目。前两步和第三步确认前，页面只
保存本次向导的临时输入和解析预览；最终提交时，由 Guidance 的项目配置用例作为事务协调者，同时协调 Appointment
写入项目基本事实、Guidance 写入项目先后关系、准备规则和患者提醒。业务结果只能是：

- Appointment 项目和 Guidance 规则全部提交成功，项目随后可以出现在资源管理和患者可选项目中；
- 任一参与方校验或写入失败，双方本次写入全部取消，前端保留用户输入并明确提示失败原因，不留下可见项目。

该事务采用 TCC 式准备、确认和取消协议。参与方可以在数据库中短暂保存带同一 `configuration_transaction_id` 的
不可见预提交记录，但这只是技术事务状态，不是 `configuring` 等业务状态；普通查询、房间关联和患者预约都不得
读取预提交数据。只有协调者确认所有参与方准备成功后才执行确认；超时、重试或部分失败时执行幂等取消。确认和
取消接口必须按事务 ID 幂等，协调者需要持久化事务进度并由恢复任务收敛未完成事务。这里不使用分布式锁代替
分布式事务：并发编辑继续依靠版本号校验，锁不能保证两个服务同时提交或同时回滚。

项目创建期间的智能解析属于无副作用的预览能力，不提前落成正式规则。工作人员明确确认“无前后关系、无准备
规则、无患者提醒”也可以完成事务，但不能跳过三个步骤直接创建项目。

已有项目修改复用同一套完整配置流程和 TCC 协调代码，不另外建立一套零散更新接口。工作人员重新走完基本信息、
前后关系和准备要求三个步骤后一次提交当前完整版本：Appointment 更新项目名称、所属科室和预计时长等基本事实，
Guidance 更新直接关系、自然语言规则、结构化准备状态和患者提醒。任一参与方失败时，双方都保留修改前版本，不能
出现患者文案已经更新、排序规则仍是旧版本，或者项目事实已经变化、Guidance 仍引用旧事实的状态。更新请求携带
双方当前版本，先完成乐观并发校验，再进入准备、确认和取消流程；创建与更新共享事务协调、幂等和故障恢复机制，
只在各参与方的本地写入动作上区分新增与替换。

房间关联、项目周窗口和容量等 Appointment 资源配置不属于这次完整项目配置事务，继续在项目创建成功后通过资源
管理单独维护。

### 先后关系表达

工作人员维护两个检查项目之间的“建议先于”方向关系。例如配置 `A -> B`，表示 A 应在 B 之前完成。系统只保存
直接关系，不使用 `previous_id`、`next_id` 把整条链写死，因此同一个项目可以有多个前置和多个后续项目。

同一条关系面向不同使用者有不同约束强度：

- 工作人员配置和 Guidance 生成院内方案时，它是必须满足的顺序约束；
- 患者查看提示时，它只是建议。系统无法知道患者是否曾在院外完成过某项检查，不能据此阻止患者操作；
- 两个项目都没有相关关系时，系统才可以按照时间和空间条件自由安排。

每条直接关系同时表达：

- 哪个项目在前、哪个项目在后；
- 规则类型；
- 工作人员查看的专业原因；
- 可选的患者可见说明。

第一版不向工作人员暴露权重、分数或算法参数。工作人员表达业务关系，Guidance 负责把关系用于规划。

### 维护权限

- 项目所属科室维护该项目的前置检查要求，权限按当前正在编辑的项目判断；
- 规则允许跨科室引用。放射科医生编辑本科室“增强 CT”时，可以把检验科“抽血”作为只读引用，配置“抽血
  建议先于增强 CT”；这只修改增强 CT 的规则，不修改抽血项目；
- 被引用的其他科室项目只提供 ID、名称和科室等选择所需事实，不能借由规则选择器进入其编辑操作；
- 其他科室可以查看与自己项目相关的规则，但不能修改对方项目的要求；现有实现中要求操作者同时拥有关系两端
  科室权限的判断需要按上述规则调整；
- 医院管理员可以管理全部规则；
- 普通患者只能看到与本次方案相关、允许患者阅读的说明。

### 与方案生成的关系

当一次方案同时包含关系两端的项目时，Guidance 必须按照该关系排序。距离更近、同楼栋或更早有号可以在不违反
关系的候选方案之间参与排序，但不能把后置项目排到前置项目之前。若方案只包含其中一个项目，则不强行补入另一
项目，只在患者侧按需要展示说明。

### 检查项目先后关系的实现结果

检查项目直接先后关系已经进入完整项目配置和方案生成流程：

- 工作人员把某个项目设为另一个项目的直接前置项目；
- 一个项目允许有多个直接前置和多个直接后续项目；
- 只保存工作人员直接配置的关系，不保存自动推导关系；
- 查询时可以从直接关系推导完整顺序链；
- 删除直接关系后，由它产生的间接关系立即自然消失；
- 新增关系时检查整张关系图，禁止直接或间接循环；
- 若新增关系会形成循环，明确拒绝并返回循环关系错误，不静默改写已有关系；
- 患者智能预约方案展示实际预约日期、大窗、房间、楼栋和可读排序原因；当日页面按 Appointment 实时状态重新展示
  当前阶段与剩余顺序。

```text
├─ rules/
│  ├─ precedence/         直接先后关系和循环校验
│  └─ description/        检查说明解析、固定状态转换和患者提醒
└─ routing/amap/          高德地点与步行路线适配
```

`rules` 是规则分类目录，`precedence` 表达项目先后关系，`description` 表达检查说明的解析与结构化转换；`planning` 只负责消费这些
规则生成方案，不反向拥有项目或预约事实。所有目录均对应已经实现的业务，不保留空包。

### 准备规则

`description` 的业务含义固定为工作人员录入的原始自然语言规则说明，不是项目用途简介。Guidance 同时保留两种
表达：患者端直接展示经过工作人员确认的自然语言；后端使用从同一文本拆解并确认后的结构化准备规则参与排序。
结构化规则不能替代原文展示，原文也不能代替后端计算。

工作人员修改 `description` 后必须重新解析，并在同一流程中确认或手工纠正结构化结果；自然语言和结构化规则
作为一个整体保存，不允许只更新患者文案却继续使用旧规则。

用于智能排序的准备规则只保留三种结构化类型：

| 类型 | 含义 | 时间表达 |
|---|---|---|
| 禁食 | 检查前保持不得进食的状态 | 弹性开始范围至本项目检查完成 |
| 禁水 | 检查前保持不得饮水的状态 | 弹性开始范围至本项目检查完成 |
| 喝水 | 为对应检查进入喝水准备状态 | 弹性开始范围至本项目检查完成，可附带“出现尿意即可检查”等提示 |

项目规则保存相对时间范围，不在项目配置时写死某个自然日期，也不把所有规则统一锚定到项目窗口开始。规划器在
项目大窗内部推导预计执行顺序和内部估算时点，再反向放置准备状态。例如客户描述“检查前 3 小时喝水”时，可以
保存为“建议提前 2～4 小时，推荐 3 小时”；患者出现明显尿意时可以提前执行，不要求精确等满 3 小时。

这些内部时点只用于比较和生成方案，不是 Appointment 承诺的精确检查时间。禁食、禁水和喝水是高优先级软排序
条件：系统尽量满足推荐值，允许在配置的浮动范围内移动，不能因为相差少量时间就直接判定整套方案不可用。每种
准备状态持续到对应检查完成；完成后不保存反向状态。

准备条件采用分级结果：完整满足推荐范围的方案优先；只能满足部分建议时仍可生成，但需要降低推荐顺序并给出
“准备时间较紧”“出现明显尿意后可前往检查”等说明。只有项目直接前后关系、Appointment 窗口、房间能力或容量
等硬条件无法满足时，才判定没有可执行方案。系统不能把软准备建议包装成强制拒绝，也不能为了生成方案而绕过硬
条件。

喝水不能当作一次瞬时动作。患者为了某项目开始喝水后，在该项目完成前都处于喝水准备状态，期间不能插入要求
禁水的项目。规划时应先完成禁食、禁水项目，再进入喝水准备阶段；如果同一大窗放不下，再尝试其他大窗或日期。

按照当前客户给出的规则，第一版智能解析采用以下归一化口径：

- “空腹”转换为从前一天 20:00 开始的禁食和禁水两条约束；
- “排空膀胱”按客户约定生成“前一天 20:00 前服用泻药”的患者提醒，并生成从 20:00 开始的禁水约束；
- “憋尿”转换为建议检查前 2～4 小时进入喝水准备状态，推荐值为 3 小时，并保留“出现明显尿意即可检查”等
  患者提示；
- 原文中的具体剂量、对象和补充说明保留在患者可见内容中，不由排序器擅自扩写。

智能解析可以后续接入外部模型，但模型只负责把自然语言提取为候选结构，不能直接产生立即生效的业务规则。完整
过程固定为“原始文本 -> 候选规则与提醒 -> 确定性格式和冲突校验 -> 工作人员确认 -> 保存”。固定且高频的表达
优先使用确定性映射；模型无法判断或输出结构不完整时，保留原文并要求工作人员处理。

解析采用封闭类型集合。模型输出的排序状态只能是禁食、禁水或喝水，不能发明“排空”“餐后”“用药状态”等新
类型；“空腹”等表达可以按固定映射展开为禁食和禁水。无法安全归入三种状态的内容只能进入患者提醒或标记为待
人工处理。服务端必须以枚举和结构校验拒绝模型返回的未知类型，不能因为外部模型输出了新名称就扩充业务模型。

工作人员可以删除误识别状态、从三种固定类型中补充遗漏状态、修改弹性提前范围与推荐值、调整就绪提示，并编辑
患者提醒。人工修正仍需通过同一结构校验；工作人员不能绕过枚举创建新状态类型。最终用于计算的是工作人员确认
后的结果，不是模型第一次输出。

### 准备规则存储

准备规则采用“一项目一条规则记录”，不把自然语言、每条状态和每条提醒拆成三套关系表。一条 Guidance 记录包含：

- Appointment 检查项目 ID；
- 患者可见的自然语言 `description`；
- 禁食、禁水、喝水组成的结构化规则 JSON；
- 患者提醒 JSON；
- 版本、更新人员和创建/更新时间。

自然语言、结构化状态和提醒在同一事务中整体保存。JSON 进入存储前必须完成枚举、时间范围和字段结构校验，不能
把未经验证的模型原始输出直接落库。规划器总是按选中项目读取整套规则，因此当前不为按单条状态跨项目检索而增加
额外关系表。项目直接前后关系仍保留在已有独立关系表中，不写入该 JSON。

该记录只保存 Appointment 项目 ID，不建立跨服务数据库外键。项目名称、科室和预计时长仍从 Appointment 后端
契约读取，Guidance 不复制项目主数据。

### 患者提醒

不能或不需要参与排序的内容统一保存为患者提醒，例如：

- 提前用药、服用泻药等带相对时间的提醒；
- 怀孕或可能怀孕、避开月经期、携带既往资料等普通提醒；
- 客户录入的其他检查前注意事项。

提醒可以带相对时间，也可以只带展示文本，但不阻止预约、不改变项目是否可选、不参与项目排序。Guidance 后续可
在预约确认、检查准备和消息页面复用这些提醒；提醒的展示时机不能反过来改变 Appointment 状态机。

### 规则修改与预约快照

工作人员不会在存在相关预约时随意修改项目规则，正常操作默认先确认该项目没有仍受影响的预约，不为少见异常建立
复杂的规则迁移或版本管理流程。作为最低限度保护，预约确认时保存本次命中的项目顺序、准备状态和患者提醒快照；
如果极端情况下规则后来发生变化，已有预约继续使用原快照，新预约使用最新规则，不回写或重新解释旧预约。

## 五、地图地点来源

### 与 Appointment 地址的分工

Appointment 继续拥有房间的院区、楼栋、楼层和房间号。这些是预约和报告使用的严格地址事实。

当前医院只有 1、2、3 号楼，三个地点均已能通过高德检索。第一版不建立医院自有的楼栋入口、侧门、无障碍入口、
电梯、楼梯或服务台模型，也不提供管理员地点标注页面。Guidance 根据 Appointment 房间中的院区和楼栋信息构造
完整楼栋名称，直接使用高德返回的对应楼栋 POI、GCJ-02 坐标和路线。楼层和房间号只在到达楼栋后作为严格地址
文字展示，不伪装成室内导航。

Guidance 不建立重复的科室、项目、房间或楼栋主数据。房间换楼栋、楼层或房间号仍由 Appointment 资源管理处理；
下一次规划按照最新严格地址重新查询高德地点。

### 检查组

在没有医学或时间冲突时，同一院区、同一楼栋的检查优先形成一个检查组。检查组只是规划过程中的组合，不改变
项目、房间或预约的业务身份。

规划先确定检查组之间是否存在必要顺序。组内项目没有专业或准备条件冲突时不提前锁定楼层和房间顺序，只记录它们
可以连续完成；时间窗口无法满足时允许拆组，不能为了保持同楼栋而生成不可执行方案。

### 第二阶段先实现两点步行路线

地图能力先收敛成一个可以被后续规划反复调用的基础操作：输入起点 A 和终点 B，返回步行路线。它只回答
“从 A 到 B 怎么走、距离多远、通常需要多久”，不接收检查项目、预约、候检人数或整套方案，也不直接决定
多个检查项目的最优顺序。

统一地点契约包含：

- 地点名称和可选地址；
- GCJ-02 纬度、经度；
- 可选的地图供应商地点标识。高德路径规划会把它作为 `origin_id` 或 `destination_id` 一并提交，
  用于增强地点和入口语义，但不能依赖它替代经纬度。

返回内容包含：

- 步行距离（米）和预计耗时（秒）；
- 按行走顺序排列的路线折线点，供小程序地图直接绘制；
- 可选的分段文字指引；
- 路线供应商标识，避免前端把供应商结果误认为医院自有数据。

两点路线验证页已经使用自建地点选择面板调用高德 POI 搜索，不再依赖 `wx.chooseLocation` 的地点库。当前验证页允许
分别搜索起点和终点；接入真实预约后，患者起点继续使用高德搜索，目的地根据预约房间的楼栋直接检索高德现有
1、2、3 号楼 POI。楼层和房间号仍作为到楼后的文字指引，不伪装成外部地图能够提供的室内路线。

当前地点检索和步行路线均使用高德 Web 服务，统一使用 GCJ-02 坐标。微信小程序原生 `<map>` 继续作为显示层，
高德只返回 POI 和路线数据，微信地图负责绘制标记和折线，因此地图视觉和交互框架保持不变。高德 Web 服务 Key
只保存在 Guidance 服务端，不下发给小程序。路线结果仍不落库，也不绕过 Appointment 读取或修改预约事实。

第一版接受高德作为三个楼栋地点和道路路线的直接来源，不再设计医院入口资料的录入、校正和长期维护流程。后端
只调用已接入的高德开放平台接口，不依赖高德网页或 App 未公开且受登录、风控保护的内部接口。高德搜索结果提供
路径规划需要的经纬度；返回 POI 标识时可以随本次地点结果继续使用，但不为此新增医院楼栋表。

这个基础操作暂不加入候检时间、项目预计时长、批量最优排序或路线矩阵。后续规划器可以在候选检查组之间多次
调用它，也可以在性能确有需要时把批量距离估算作为 Guidance 内部优化，但不能改变这个稳定的 A 到 B 契约。

当前实现不新增数据库表：地点搜索和道路路线按请求实时计算并返回。App API 对患者提供受登录保护的地点搜索与
两点步行路线入口，小程序只持有普通地点坐标和高德 POI 标识；高德服务端 Key 始终停留在 Guidance 服务。

## 六、接收患者规划条件

患者发起一次规划时提供：

- 一个或多个检查项目；
- 一个或多个可以不连续的可到院日期；
- 每个日期分别选择全天、上午或下午；
- 可选的出发位置；
- 可选的交通方式；
- 综合推荐、尽快完成或少跑医院之一。

日期必须按照患者实际选择的离散集合处理，不能把多个日期错误扩成连续日期范围。

出发位置不是生成方案的强制条件。没有位置时仍然生成检查时间和院内顺序，但不得声称已经计算出最优到院通勤
路线。

规划每个目标日期时，Guidance 读取患者当天全部预约事实，不只读取仍待检查的预约，也不扫描与本次计算无关的
更早历史。所有准备状态和本阶段的项目顺序要求都限定在一天内，因此当天信息已经构成完整规划上下文：

- 已完成或报告待完成的检查作为当天已经发生的事实，可以满足“已经先做某项目”等顺序条件；
- 待报到、排队中、正在叫号和检查中的预约作为不能由 Guidance 移动的既定安排；
- 已取消、未到场等记录仍会被读取，但因为检查没有实际发生，不视为已满足项目顺序或准备要求；
- 本次新选择的项目只能围绕上述事实安排，不能修改、取消或重新分配已有预约。

## 七、形成可行检查组合

Guidance 根据患者条件，从 Appointment 提供的项目、房间和当前可预约事实中，为每个项目寻找可执行组合。一个
候选组合至少需要同时满足：

- 项目属于患者选择范围；
- 房间能够执行该项目；
- 日期和上午/下午属于患者可到院范围；
- 项目窗口与房间窗口有效；
- 当前仍有可用容量；
- 不违反 Appointment 的重复预约和每周额度等限制；
- 第一版所有项目位于同一院区。

Guidance 可以提前排除明显不可行的组合，但最终资格和容量仍由 Appointment 在创建预约时裁决。

## 八、分组、排序和比较方案

### 统一优先级

方案按照下列业务优先级形成：

1. 必须遵守的医学先后关系；
2. 尽可能先完成禁食、禁水等带禁止事项的检查，再安排喝水和无禁止事项的检查；
3. 可预约窗口、停止新增时间和检查结束时间；
4. 准备条件相同的项目尽量成组连续完成；
5. 尽量在同一楼栋连续完成，减少跨楼栋、重复上下楼和无意义移动；
6. 患者选择的日期及“综合、尽快、少跑医院”偏好。

项目预计时长用于估算安排和展示，不代表真实排队时间，也不控制 Appointment 的现场检查。

智能预约不使用候选日期当前已经预约的人数或预计工作量来预测未来排队，只把容量是否仍可预约作为可执行性条件。
它提供的是日期、大窗、准备分组和楼栋组合构成的宏观全局方案，默认患者到达后进入正常现场流程，不把未来排队
波动伪装成可以提前准确比较的方案优势。

出发位置已知时，规划在所有仍满足医学和时间约束的检查组之间比较到达路线，选择更适合作为起点的检查组；
进入楼栋后再比较组内楼层和房间移动。出发位置未知时，先形成可行的检查组和候选顺序，等患者提供位置后再补充
路线比较。外部地图是否能够直接支持全部遍历和院内定位，需要在地图能力评审中验证，不能提前假设供应商一定
支持。

### 三类患者偏好

- **综合推荐**：在可完成时间、到院次数和移动距离之间取得平衡；
- **尽快完成**：优先更早完成全部检查，可以接受更多移动或多次到院；
- **少跑医院**：优先同一天、同院区、同楼栋完成，可以接受稍晚日期。

院内少走路是所有方案都会考虑的共同目标，不要求患者理解或配置算法权重。

### 推荐结果

一次最多返回三个确实存在差异的方案。每个方案都要说明：

- 使用哪些日期、需要到院几次；
- 每个项目的日期、大窗、房间和严格地址；
- 必要先后关系、可自由调整的检查集合和预计检查总时长；
- 项目之间的移动关系；
- 命中的医学规则；
- 为什么推荐该方案，以及相对其他方案付出了什么代价。

如果只存在一个可行方案，就只返回一个；不能为了凑足数量生成内容相同或不可执行的方案。

方案完整满足准备建议时正常展示；使用弹性范围或未达到推荐值时，卡片必须说明降级点和患者需要观察的就绪提示，
但仍允许患者选择。硬条件不满足的组合不进入推荐结果。

如果项目直接关系、准备状态、Appointment 窗口和患者所选日期范围组合后不存在可执行方案，系统不能忽略规则或
伪造降级方案。患者端不披露具体冲突项目、内部规则结构或算法推导，只统一返回“当前选择无法生成推荐，请重新
选择日期范围”。工作人员方案试算则保留完整冲突链，指出涉及的项目、直接关系、准备状态和窗口，便于检查错误
配置。两端读取的是同一次求解结果，只是错误信息的展示粒度不同。

## 九、整套确认并创建预约

患者选择方案后，一次确认其中全部项目。业务结果只能是：

- 全部预约成功；或
- 一条也不创建，并告知方案已经失效，需要重新计算。

不能出现部分项目预约成功、其余失败的残缺方案。确认时如果容量、窗口、重复预约状态或周额度已经变化，
Appointment 拒绝整套创建，Guidance 使用最新事实重新生成方案。

创建成功后，每一项仍然是普通 Appointment 预约：

- 患者继续在“我的预约”查看；
- 科室工作人员继续在“科室预约”处理；
- 报到、叫号、检查、报告和消息全部沿用 Appointment；
- 不新增面向患者的“方案管理”或“方案历史”业务。

## 十、预约后检查导航

检查导航读取患者已经存在的预约，不要求预约必须由 Guidance 创建。因此单项预约、患者分别创建的多项预约和
智能导诊整套创建的预约，都能进入同一导航能力。智能预约阶段只在内部使用路线比较，不展示完整路线，也不提前
确定没有业务关系的项目顺序；预约确认后，当日检查路线才从当前可执行集合中选择下一站，并展示真实 A 到 B 路线。

### 检查前

按日期组织预约，展示院区、检查准备事项、建议到院时间和外部地图到院路线。患者此前没有提供位置时，可以在
这里再次提供当前位置或出发点。

### 检查当天

Guidance 综合当天预约、医学顺序、项目窗口、预计时长、严格地址和当前位置，给出：

- 当前下一项检查；
- 前往院区、楼栋、楼层和房间的路线；
- 已完成、当前和剩余检查；
- 当前推荐顺序及每一步原本的推荐原因。

患者不手工标记检查完成。Appointment 的报到、排队、叫号、检查中、报告待完成等状态是检查进度事实，
Guidance 只读取并据此推进导航。

- 待报到预约属于仍待完成项目；
- 已经排队、正在叫号或检查中的预约由 Appointment 现场流程控制，Guidance 不引导患者离开当前现场去执行其他项目；
- 报告待完成表示实际检查已经结束，与已完成预约一样不再进入剩余检查顺序；
- 已取消和未到场预约不再作为当天可执行检查继续导航。

### 动态调整边界

Guidance 可以调整剩余检查的建议顺序，但不能自行修改已经预约的日期、上午/下午或房间。需要改变预约事实时，
必须重新让患者确认并交由 Appointment 执行。

Guidance 不预测“先做 B 后是否还能在 A 的原窗口结束前完成”，也不因为某个窗口更早结束就机械地把该项目排在
前面。现场排队和检查耗时受不可控因素影响，这类估算既不稳定，也不是导航需要解决的问题。患者一旦完成检查报到，
Appointment 会把未叫到的患者保留在房间候检队列中；上午遗留队列可以在下午继续叫号和检查。因此项目窗口在
智能预约阶段用于判断能否创建预约，在检查当天不作为 Guidance 抢排下一站的倒计时。

动态路线可以读取候检队列、叫号进度和检查执行情况。只有多个下一站在直接顺序、准备状态、可执行窗口和地点等
主要条件下都同样合适时，才以现场待检查人数和预计时长形成相对工作量，选择预计更快完成的下一站。简单场景可以
理解为“当前人数 × 预计时长”；同一队列混有不同时长项目时，优先累加各预约的预计时长快照。前端只展示“预计
更快完成”或“当前检查负担较轻”等相对结论，不承诺精确等待分钟，也不能据此引导已经排队、正在叫号或检查中的
患者离开当前现场。

## 十一、工作人员方案试算

工作人员可以选择若干检查项目、可到院日期和模拟出发点，使用与患者相同的规划逻辑查看：

- 形成了哪些检查组；
- 命中了哪些硬规则和软规则；
- 哪些项目因时间或地点被拆组；
- 患者最终会看到哪些方案和解释；
- 修改规则或地点后，结果是否符合预期。

方案试算只验证 Guidance 配置，不创建真实预约，也不复制 Appointment 的科室预约、叫号和检查工作台。

## 十二、服务分工

| 能力 | 业务负责方 |
|---|---|
| 账号、科室、工作人员身份和授权范围 | Identity |
| 项目名称、所属科室、房间、严格地址、窗口、容量和预计时长 | Appointment |
| 预约、报到、候检、叫号、检查、报告和消息状态 | Appointment |
| 自然语言规则说明、医学顺序规则、准备条件、患者提醒、楼栋 POI 解析、检查分组和推荐逻辑 | Guidance |
| 地点检索、到院通勤距离、时间和道路路线 | 高德 Web 服务，由 Guidance 封装 |
| 页面入口、身份视图和结果组合 | App API 与小程序 |

服务之间不通过前端传递业务事实。小程序只提交患者选择，App API 负责对外入口；Guidance 在后端按照明确契约
读取所需事实，Appointment 仍是预约成功与否的唯一裁决者。

## 十三、第一版明确不做

- 跨院区组合规划；
- 把候检人数直接换算成精确等待时间；
- 医生排班、医生选择或医生容量；
- 人工插队、急诊权重或设备故障调度；
- 自动改变已经创建的预约；
- 第二套预约、叫号、检查或报告状态机；
- 面向患者的方案列表、方案历史和方案 CRUD；
- 把候检时间、项目预计时长或检查顺序塞入两点路线接口；
- 由地图供应商直接生成整套检查方案；
- 将地图供应商路线结果长期落库或向小程序暴露服务端 Key。

## 十四、当前确认状态

第一版业务规则已经足以进入实现，没有仍会阻塞数据模型或主流程的待确认项。“预计完成时间”此前已经明确不作为
当前功能：项目预计时长只用于内部相对排序和项目本身的静态展示，不推导患者准确完成时刻。等未来具备可靠现场
执行模型后，再单独讨论是否增加这项扩展，当前实现不得提前加入。
