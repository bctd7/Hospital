# Guidance 智能导诊业务逻辑

> 状态：产品主线和第一版边界已经确认；第一阶段“检查项目先后关系”已经实现。本文重点回答 Guidance 要完成
> 哪些业务功能、功能之间如何衔接，以及它与 Appointment、Identity 和地图能力如何分工。后续地图、方案生成和
> 导航算法仍需逐步讨论，不在第一阶段提前定死。

## 一、业务目标

Guidance 是独立服务，把原先分开的“检查顺序”和“地图导航”合并为一项连续能力：

1. 预约前，为患者选择的多个检查项目生成少量可行、可解释的预约方案；
2. 预约确认时，把选中方案转换成一组普通 Appointment 预约；
3. 预约后，基于已经存在的预约生成到院路线、院内顺序和下一站指引；
4. 检查过程中，根据 Appointment 的真实状态变化推进剩余行程；
5. 为工作人员提供顺序规则、地点标注和方案试算能力。

Guidance 不取代 Appointment。它负责“怎样组合和推荐”，Appointment 继续负责“项目能否预约、容量是否足够、
预约处于什么状态”。

## 二、完整业务闭环

```text
工作人员维护顺序规则和地点标注
  -> 患者选择检查项目、可到院日期和偏好
  -> Guidance 读取项目、房间、窗口、号源和地点事实
  -> 排除不可行组合
  -> 按医学顺序、时间和空间形成检查组
  -> 生成不超过三个可解释方案
  -> 患者选择并一次确认整套方案
  -> Appointment 原子创建全部预约
  -> Guidance 从普通预约生成检查导航
  -> Appointment 状态变化推动下一站更新
```

其中任何推荐都不能绕过 Appointment 的容量、重复预约、每周额度、时间窗口和状态机校验。

## 三、功能一：维护医学顺序规则

### 3.1 规则表达

工作人员维护两个检查项目之间的“建议先于”方向关系。例如配置 `A -> B`，表示 A 应在 B 之前完成。系统只保存
直接关系，不使用 `previous_id`、`next_id` 把整条链写死，因此同一个项目可以有多个前置和多个后续项目。

同一条关系面向不同使用者有不同约束强度：

- 工作人员配置和 Guidance 生成院内方案时，它是必须满足的顺序约束；
- 患者查看提示时，它只是建议。系统无法知道患者是否曾在院外完成过某项检查，不能据此阻止患者操作；
- 两个项目都没有相关关系时，系统才可以按照时间和空间条件自由安排。

每条直接关系同时表达：

- 哪个项目在前、哪个项目在后；
- 规则类型；
- 工作人员查看的专业原因；
- 可选的患者可见说明。

第一版不向工作人员暴露权重、分数或算法参数。工作人员表达业务关系，Guidance 负责把关系用于规划。

### 3.2 维护权限

- 项目所属科室维护该项目的前置检查要求；
- 其他科室可以查看与自己项目相关的规则，但不能修改对方项目的要求；
- 医院管理员可以管理全部规则；
- 普通患者只能看到与本次方案相关、允许患者阅读的说明。

### 3.3 与方案生成的关系

当一次方案同时包含关系两端的项目时，Guidance 必须按照该关系排序。距离更近、同楼栋或更早有号可以在不违反
关系的候选方案之间参与排序，但不能把后置项目排到前置项目之前。若方案只包含其中一个项目，则不强行补入另一
项目，只在患者侧按需要展示说明。

### 3.4 第一阶段实现结果

第一阶段只实现检查项目的直接先后关系，不实现地图、方案生成和预约后导航：

- 工作人员把某个项目设为另一个项目的直接前置项目；
- 一个项目允许有多个直接前置和多个直接后续项目；
- 只保存工作人员直接配置的关系，不保存自动推导关系；
- 查询时可以从直接关系推导完整顺序链；
- 删除直接关系后，由它产生的间接关系立即自然消失；
- 新增关系时检查整张关系图，禁止直接或间接循环；
- 若新增关系会形成循环，明确拒绝并返回循环关系错误，不静默改写已有关系；
- 患者侧如何展示顺序提示留到 Guidance 页面接入时实现，本阶段先形成可靠规则事实。

目录按规则含义组织，不建立含义宽泛的平级 Manager：

```text
service/guidance/rpc/internal/
└─ rules/
   └─ precedence/
      ├─ model.go
      ├─ errors.go
      ├─ store.go
      └─ manager/
         ├─ manager.go
         ├─ create.go
         ├─ delete.go
         ├─ list.go
         └─ validation.go
```

`rules` 是规则分类目录，`precedence` 明确表示检查项目先后顺序。以后只有在另一类规则被确认并开始实现时，才
增加新的同级包；第一阶段不创建 `map`、`planning` 或 `navigation` 空目录。

## 四、功能二：维护导航地点语义

### 4.1 与 Appointment 地址的分工

Appointment 继续拥有房间的院区、楼栋、楼层和房间号。这些是预约和报告使用的严格地址事实。

Guidance 只补充导航所需语义，例如：

- 房间在地图或楼层图上的位置；
- 院区和楼栋入口；
- 电梯、楼梯、服务台等地标；
- 地标之间可通行的路线信息；
- 外部地图到院路线与院内路线之间的衔接点。

Guidance 不再建立一套重复的科室、项目、房间主数据。房间停用、换楼层或更改严格地址仍由 Appointment 资源
管理处理，地点标注随之重新校验。

### 4.2 检查组

在没有医学或时间冲突时，同一院区、同一楼栋的检查优先形成一个检查组。检查组只是规划过程中的组合，不改变
项目、房间或预约的业务身份。

规划先比较检查组之间的顺序，再安排组内楼层和房间顺序。时间窗口无法满足时允许拆组，不能为了保持同楼栋而
生成不可执行方案。

## 五、功能三：接收患者规划条件

患者发起一次规划时提供：

- 一个或多个检查项目；
- 一个或多个可以不连续的可到院日期；
- 每个日期分别选择全天、上午或下午；
- 可选的出发位置；
- 可选的交通方式；
- 综合推荐、尽快完成或少跑医院之一。

日期必须按照患者实际选择的离散集合处理，不能把多个日期错误扩成连续日期范围。

出发位置不是生成方案的强制条件。没有位置时仍然生成检查时间和院内顺序，但不得声称已经计算出最优到院通勤
路线。

## 六、功能四：形成可行检查组合

Guidance 根据患者条件，从 Appointment 提供的项目、房间和当前可预约事实中，为每个项目寻找可执行组合。一个
候选组合至少需要同时满足：

- 项目属于患者选择范围；
- 房间能够执行该项目；
- 日期和上午/下午属于患者可到院范围；
- 项目窗口与房间窗口有效；
- 当前仍有可用容量；
- 不违反 Appointment 的重复预约和每周额度等限制；
- 第一版所有项目位于同一院区。

Guidance 可以提前排除明显不可行的组合，但最终资格和容量仍由 Appointment 在创建预约时裁决。

## 七、功能五：分组、排序和比较方案

### 7.1 统一优先级

方案按照下列业务优先级形成：

1. 必须遵守的医学先后关系；
2. 可预约窗口、停止新增时间和检查结束时间；
3. 尽量在同一楼栋连续完成；
4. 减少跨楼栋、重复上下楼和无意义移动；
5. 患者选择的日期及“综合、尽快、少跑医院”偏好。

项目预计时长用于估算安排和展示，不代表真实排队时间，也不控制 Appointment 的现场检查。

出发位置已知时，规划在所有仍满足医学和时间约束的检查组之间比较到达路线，选择更适合作为起点的检查组；
进入楼栋后再比较组内楼层和房间移动。出发位置未知时，先形成可行的检查组和候选顺序，等患者提供位置后再补充
路线比较。外部地图是否能够直接支持全部遍历和院内定位，需要在地图能力评审中验证，不能提前假设供应商一定
支持。

### 7.2 三类患者偏好

- **综合推荐**：在可完成时间、到院次数和移动距离之间取得平衡；
- **尽快完成**：优先更早完成全部检查，可以接受更多移动或多次到院；
- **少跑医院**：优先同一天、同院区、同楼栋完成，可以接受稍晚日期。

院内少走路是所有方案都会考虑的共同目标，不要求患者理解或配置算法权重。

### 7.3 推荐结果

一次最多返回三个确实存在差异的方案。每个方案都要说明：

- 使用哪些日期、需要到院几次；
- 每个项目的日期、大窗、房间和严格地址；
- 推荐检查顺序和预计完成时间；
- 项目之间的移动关系；
- 命中的医学规则；
- 为什么推荐该方案，以及相对其他方案付出了什么代价。

如果只存在一个可行方案，就只返回一个；不能为了凑足数量生成内容相同或不可执行的方案。

## 八、功能六：整套确认并创建预约

患者选择方案后，一次确认其中全部项目。业务结果只能是：

- 全部预约成功；或
- 一条也不创建，并告知方案已经失效，需要重新计算。

不能出现部分项目预约成功、其余失败的残缺方案。确认时如果容量、窗口、重复预约状态或周额度已经变化，
Appointment 拒绝整套创建，Guidance 使用最新事实重新生成方案。

创建成功后，每一项仍然是普通 Appointment 预约：

- 患者继续在“我的预约”查看；
- 科室工作人员继续在“科室预约”处理；
- 报到、叫号、检查、报告和消息全部沿用 Appointment；
- 不新增面向患者的“方案管理”或“方案历史”业务。

## 九、功能七：预约后检查导航

检查导航读取患者已经存在的预约，不要求预约必须由 Guidance 创建。因此单项预约、患者分别创建的多项预约和
智能导诊整套创建的预约，都能进入同一导航能力。

### 9.1 检查前

按日期组织预约，展示院区、检查准备事项、建议到院时间和外部地图到院路线。患者此前没有提供位置时，可以在
这里再次提供当前位置或出发点。

### 9.2 检查当天

Guidance 综合当天预约、医学顺序、项目窗口、预计时长、严格地址和当前位置，给出：

- 当前下一项检查；
- 前往院区、楼栋、楼层和房间的路线；
- 已完成、当前和剩余检查；
- 下一站发生变化时的原因。

患者不手工标记检查完成。Appointment 的报到、排队、叫号、检查中、报告待完成等状态是检查进度事实，
Guidance 只读取并据此推进导航。

- 待报到预约属于仍待完成项目；
- 已经排队、正在叫号或检查中的预约由 Appointment 现场流程控制，Guidance 不引导患者离开当前现场去执行其他项目；
- 报告待完成表示实际检查已经结束，与已完成预约一样不再进入剩余检查顺序；
- 已取消和未到场预约不再作为当天可执行检查继续导航。

### 9.3 动态调整边界

Guidance 可以调整剩余检查的建议顺序，但不能自行修改已经预约的日期、上午/下午或房间。需要改变预约事实时，
必须重新让患者确认并交由 Appointment 执行。

第一版不根据候检人数排序，也不预测等待分钟。现实中人数少不代表速度快，在缺少可靠执行时间模型时不能把
候检数量包装成准确等待时间。

## 十、功能八：工作人员方案试算

工作人员可以选择若干检查项目、可到院日期和模拟出发点，使用与患者相同的规划逻辑查看：

- 形成了哪些检查组；
- 命中了哪些硬规则和软规则；
- 哪些项目因时间或地点被拆组；
- 患者最终会看到哪些方案和解释；
- 修改规则或地点后，结果是否符合预期。

方案试算只验证 Guidance 配置，不创建真实预约，也不复制 Appointment 的科室预约、叫号和检查工作台。

## 十一、服务分工

| 能力 | 业务负责方 |
|---|---|
| 账号、科室、工作人员身份和授权范围 | Identity |
| 项目、房间、严格地址、窗口、容量和预计时长 | Appointment |
| 预约、报到、候检、叫号、检查、报告和消息状态 | Appointment |
| 医学顺序规则、地点标注、检查分组和推荐逻辑 | Guidance |
| 到院通勤距离、时间和道路路线 | 外部地图能力，由 Guidance 使用 |
| 页面入口、身份视图和结果组合 | App API 与小程序 |

服务之间不通过前端传递业务事实。小程序只提交患者选择，App API 负责对外入口；Guidance 在后端按照明确契约
读取所需事实，Appointment 仍是预约成功与否的唯一裁决者。

## 十二、第一版明确不做

- 跨院区组合规划；
- 基于候检人数或预测等待时间的调度；
- 医生排班、医生选择或医生容量；
- 人工插队、急诊权重或设备故障调度；
- 自动改变已经创建的预约；
- 第二套预约、叫号、检查或报告状态机；
- 面向患者的方案列表、方案历史和方案 CRUD；
- 预先绑定某一家地图供应商或某一种求解算法。

## 十三、后续逐项确认

以下问题尚未在现有讨论中形成最终结论，不能提前写成实现要求：

1. 整套预约成功后，检查导航以“患者选中的原方案顺序”为初始基准，还是每次都从普通预约重新计算；
2. 多条硬性顺序规则形成冲突或循环时，保存阶段如何提示和由谁裁决；
3. 检查准备事项除了患者可见文字外，是否需要形成能够影响规划的结构化条件；
4. 院内地图第一版做到楼栋级、楼层级还是房间级，以及外部地图与院内地图在哪里交接；
5. 在不预测排队时间的前提下，“预计完成时间”具体包含哪些时间组成。

后续讨论继续一次确认一个问题。确认后的结论进入对应章节，技术实现细节在业务规则稳定后再设计。
