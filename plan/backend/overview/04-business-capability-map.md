# 后端业务能力全景

> 状态：当前有效业务边界；具体预约规则见
> [Appointment 预约检查服务 Plan](../modules/01-appointment-and-examination-booking.md)。

## 1. 患者侧能力

### 本人信息

使用已验证手机号建立或匹配首期本人账号/档案。首期不管理家庭成员，不按未验证手机号查询他人数据。

### Appointment

管理检查项目及其固态时间约束、科室窗口、活动容量、独立预约、建议顺序、取消、限制和惩罚、报到、
排队、叫号、检查开始与完成。相同项目、同日和重叠窗口预约允许存在，每条预约独立承担状态和惩罚。

### Navigation

管理地点、楼层图、路线和地图版本，为预约详情和到院过程提供位置指引。

### Report

将每次完成的检查关联到报告，管理生成中、发布、更正、撤回、附件和患者访问权限。报告发布晚于检查
完成，不影响 Appointment 释放活动容量。

### Message

管理预约、限制、叫号和报告事件产生的站内通知、投递记录和阅读状态。微信订阅消息是投递渠道，不替代
站内消息事实。

## 2. 工作人员侧能力

- Identity：账号、手机号认证、角色、permissions、医院、院区、科室和医生身份；
- Appointment 管理：检查目录、前置条件、窗口、容量、队列、叫号、执行和处罚处理；
- Navigation 管理：地点、地图和路线；
- Report 管理：报告录入/同步、审核、发布、更正、撤回和导出；
- 审计与运维：高风险操作、跨部门访问、人工加黑/解禁和报告变更审计。

前端菜单差异不能替代业务服务鉴权，不为“我的预约”“报告查询”等页面入口分别复制业务服务。

## 3. 主流程

```text
手机号登录并取得本人身份
  -> 选择一个检查项目
  -> 阅读并确认检查前置条件
  -> 选择科室的上午/下午到院窗口
  -> 独立创建预约并占用活动容量
  -> 报到、排队和叫号
  -> 医生开始并结束检查
  -> 释放活动容量
  -> 生成和发布报告
  -> 患者查看报告
```

每个检查项目独立预约。系统可以给出跨项目建议顺序，但不生成总订单，不自动创建、取消或修改预约。

## 4. 数据原则

- 账号、本人、科室、项目、预约、执行和报告使用内部稳定 ID；
- 手机号是首期本人匹配依据，但明文手机号不作为业务表外键；
- 当前状态和状态历史分开；
- 预约保存项目、前置条件版本、地点和窗口快照；
- 报告保留版本，更正不覆盖历史；
- 服务只写自己拥有的数据；
- 跨服务使用稳定 ID、快照、RPC 和事件，不跨库联表；
- 关键写操作具有幂等、审计和 request ID；
- 首期使用版本化固态时间约束图，不把条件拆成固定布尔列；未来动态语义必须带 Schema、Evaluator 和版本。

## 5. 当前待客户确认

- 报到、叫号、过号和失约认定；

- 本人内部 ID 与手机号换绑、号码回收和历史归属；
- 地图和真实医院系统的接入深度。
