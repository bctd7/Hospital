# 后端业务能力全景

> 状态：当前有效业务边界；具体预约规则见
> [Appointment 预约检查服务 Plan](../modules/01-appointment-and-examination-booking.md)。

## 1. 患者侧能力

### 本人信息

使用已验证手机号建立或匹配首期本人账号/档案。首期不管理家庭成员，不按未验证手机号查询他人数据。

### Appointment

管理检查项目及其文字描述、检查房间、房间—项目关系、独立周配置、后续结构化时间约束、房间共享活动容量、独立预约、建议顺序、取消、限制和惩罚、报到、
排队、叫号、检查开始与完成。相同项目、同日和重叠窗口预约允许存在，每条预约独立承担状态和惩罚。

### Report

Appointment 内部将一次预约和一次检查绑定到唯一报告主体，管理草稿、首版发布、不可覆盖的更正版本和患者
本人访问。首版报告发布与检查完成、容量释放在同一事务提交；附件、撤回和多人审核不在当前范围。

### Message

管理预约、限制、叫号和报告事件产生的站内通知、投递记录和阅读状态。微信订阅消息是投递渠道，不替代
站内消息事实。

## 2. 工作人员侧能力

- Identity：账号、手机号认证、角色、permissions、医院、院区、科室和医生身份；
- Appointment 管理：检查目录、房间、房间—项目关系、独立周配置、容量、队列、叫号、执行和处罚处理；
- Report 管理：报告草稿、完成并发布、正式版查看、更正和版本历史；
- 审计与运维：高风险操作、跨部门访问、人工加黑/解禁和报告变更审计。

前端菜单差异不能替代业务服务鉴权，不为“我的预约”“报告查询”等页面入口分别复制业务服务。

## 3. 主流程

```text
手机号登录并取得本人身份
  -> 选择科室和一个检查项目
  -> 阅读并确认检查前置条件
  -> 选择能执行该项目的检查房间
  -> 选择本周上午/下午到院窗口
  -> 独立创建预约并占用活动容量
  -> 报到、排队和叫号
  -> 授权科室工作人员开始检查
  -> 完成检查、发布首版报告并释放活动容量
  -> 患者查看报告
```

每个检查项目独立预约。系统可以给出跨项目建议顺序，但不生成总订单，不自动创建、取消或修改预约。

## 4. 数据原则

- 账号、本人、科室、项目、预约、执行和报告使用内部稳定 ID；
- 手机号是首期本人匹配依据，但明文手机号不作为业务表外键；
- 当前状态和状态历史分开；
- 预约保存项目、前置条件版本、科室、房间和两类窗口快照；
- 报告保留版本，更正不覆盖历史；
- 服务只写自己拥有的数据；
- 跨服务使用稳定 ID、快照、RPC 和事件，不跨库联表；
- 关键写操作具有幂等、审计和 request ID；
- 第一实施阶段只保存版本化文字描述；未来结构化结果必须绑定来源描述版本、Schema、审核状态和 Evaluator 版本。

## 5. 当前待客户确认

- 报到、叫号、过号和失约认定；
- AI 提取 Schema、固定事件、人工审核、规则发布流程、排序优化目标和建议顺序展示；
- 项目报告模板、患者搜索展示标识，以及报告中科室、院区和工作人员名称的稳定快照；
- 本人内部 ID 与手机号换绑、号码回收和历史归属；
- 检查顺序所需移动信息和真实医院系统的接入深度。
