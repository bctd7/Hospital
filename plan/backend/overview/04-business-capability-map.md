      ·   # 后端业务能力全景

> 状态：总体业务边界，具体模块按交付路线逐步细化

## 1. 患者侧模块

### Patient

保存当前账号本人的业务资料和稳定 `patient_profile_id`。首版不管理家庭成员，不通过手机号自动
匹配医院历史患者。Identity 负责登录账号和手机号，Patient 负责医疗业务所需的本人资料。

### Appointment

负责预约申请、项目、号源/容量占用、确认、取消、改签和状态历史。预约创建时绑定稳定账号与
患者档案，不把手机号作为业务外键。当前只设计预约主流程和状态历史。

### Planning

根据检查项目、准备条件、位置、时间窗和规则生成可解释的检查顺序方案。保存输入快照、规则
版本、算法版本和输出，支持业务变化后的重新规划但不改写已发生历史。

### Navigation

管理院内地点、节点、路径和地图版本，为患者路线和规划成本提供稳定位置数据。首版不把地图
编辑能力与患者导航接口混在同一权限范围。

### Report

管理本系统检查链路产生的报告、版本、发布、更正、下载和导出。历史医院报告接入必须先完成
可靠的患者主索引绑定，不能按手机号直接查询。

### Message

管理预约提醒、系统通知、公告投递、已读状态和未读计数。小程序订阅消息属于投递渠道，不替代
站内消息事实。

## 2. 工作人员与平台模块

### Identity 与组织

账号、手机号认证、角色、permissions、部门和医生身份开通由 Identity 负责。医生和超级管理员
复用工作人员前端框架，超级管理员后续额外拥有身份录入和组织管理入口。

### 业务管理

工作人员端按 permission 组合 Appointment、Planning、Navigation、Report 等模块能力，不新建
一套复制数据的“后台服务”。前端菜单差异不能代替业务服务鉴权。

### 审计与运维

身份授权、跨部门访问、报告发布更正、规则发布和高风险导出需要业务审计；运行日志、指标、
Trace 和告警属于可观测性，不与不可变业务审计混为一张表。

## 3. 主流程

```text
手机号登录
  -> 完成本人资料
  -> 浏览检查项目/科室/排班
  -> 创建预约
  -> 生成或调整检查顺序
  -> 院内导航与检查执行
  -> 报告发布
  -> 消息提醒与历史查询
```

当前优先打通“一个本人、一个检查项目、一次预约”的最小闭环，再扩展多项目规划、地图与报告。

## 4. 数据关系原则

- 账号、患者档案、部门、项目、预约、方案、报告使用稳定内部 ID；
- 当前状态与状态历史分开；
- 预约、方案和报告保存必要快照；
- 服务只写自己拥有的数据；
- 跨服务引用保存 ID 和必要快照，不直接外键到其他服务数据库；
- 关键写操作具有幂等键、审计和可追踪 request ID；
- 医疗历史与审计记录不因普通删除操作物理消失。

## 5. 暂未确认

- 医院患者主索引和历史报告绑定方式；

- 多医院/多租户切换和医生多部门任职。单医院下的多院区属于已确认首期范围。
