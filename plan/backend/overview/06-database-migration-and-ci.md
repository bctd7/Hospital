# 数据库迁移与 CI 基线

> 状态：Identity 首期已实施；新业务服务按相同规则接入

本文记录为什么采用当前迁移与检查方案，以及后续模块必须遵守的工程规则。具体命令见
`scripts/README.md`，当前迁移清单见 `migrations/README.md`；这里不重复充当启动手册。

## 1. 已完成基线

- 使用 `golang-migrate` 风格的 `*.up.sql` / `*.down.sql` 管理数据库版本；
- Identity 拥有独立迁移目录和逻辑数据库，当前迁移为 `000001` 至 `000005`；
- 本地建库、迁移与版本查询由 PowerShell 脚本统一执行；
- `scripts/check.ps1` 统一校验 Go、契约、Compose、小程序测试、类型和构建；
- GitHub CI 使用同一工程规则，不依赖开发者电脑已有数据库或 `node_modules`；
- Compose 初始化只负责全新数据卷，已有数据库升级必须走正式迁移。

## 2. 设计决定

### 2.1 建库与迁移分权

```text
本地数据库引导
  -> 创建逻辑数据库和服务账号
  -> 仅本地需要高权限

服务迁移
  -> 使用该服务数据库账号
  -> 只升级本服务拥有的表
```

生产数据库和账号由部署流程创建，普通服务和迁移任务不得持有跨库或生产 root 权限。

### 2.2 服务拥有数据

每个进入开发阶段的业务服务才创建自己的逻辑数据库、迁移目录和最小权限账号。服务之间不建立
跨库外键、联表或触发器；跨服务状态通过 RPC 或事件传播。

未实施的 Patient、Appointment、Planning、Report 和 Navigation 不预建空数据库或空迁移目录。

### 2.3 迁移历史不可改写

进入共享分支或已在环境执行的迁移不可直接修改，修正必须追加新版本。破坏性字段变化采用：

```text
新增兼容结构 -> 双写或回填 -> 切换读取 -> 后续版本删除旧结构
```

业务样例数据不写入结构迁移；稳定系统角色和权限可以作为 Identity 基础数据随迁移维护。

## 3. 失败与安全规则

- 找不到工具、DSN、迁移目录或出现 dirty migration 时立即失败；
- 命令输出不得打印密码、验证码、Token 或完整连接串；
- `up` 是默认方向，`down` 必须显式指定步数；
- 生产回滚不由普通开发脚本自动执行；
- 任一测试、契约校验、迁移或构建失败时，统一检查和 CI 返回非零状态；
- CI 不连接开发或生产数据库，也不读取仓库外的个人环境文件。

## 4. 新服务接入顺序

1. 明确服务和数据所有权；
2. 创建独立迁移目录与第一版可回滚迁移；
3. 将服务加入迁移脚本白名单；
4. 在空库执行完整 `up`，再验证最近版本 `down -> up`；
5. 将测试和迁移 smoke test 接入统一检查；
6. 更新对应 README 的运行入口和迁移清单。

## 5. 完成标准

- 空库可一条命令升级到最新结构，重复 `up` 不破坏数据；
- 已存在数据库只执行未应用版本；
- 可以安全查询当前版本并识别 dirty 状态；
- 服务账号只拥有本库权限；
- 本地检查与 CI 对同一代码得到一致结论；
- 新增迁移不会依赖删除数据卷、手工粘贴 SQL 或修改旧迁移。

生产自动部署、备份恢复、不可逆迁移审批、云 Secret Manager 和 Kafka 集成测试属于部署基础设施的
独立工作，不在本基线中伪装为已经完成。
