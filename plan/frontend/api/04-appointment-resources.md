# Appointment 检查项目与资源接口消费方案

> 状态：管理端检查项目、房间、项目关系和两套周配置接口均已实现，可直接接入；患者端项目目录接口待补。
>
> 准确路径、字段和错误码以 `contracts/api/` 与生成的 OpenAPI 为准。本文只规定前端消费边界。

## 1. 两套前端不是同一页面

Appointment 的底层事实只有一套，但前端必须提供两个方向完全不同的视图：

```text
管理端首页：院区 -> 科室（部门） -> 房间 -> 当前房间可执行项目
管理详情：房间 -> 项目关系、房间开放窗口
          项目 -> 项目基本信息、项目预约窗口

患者端：院区 -> 科室 -> active 检查项目 -> active 可选房间
              -> 预约日期、容量与提交（后续阶段）
```

管理端以维护为目标，展示状态、版本、停用资源和编辑入口；患者端以理解和选择为目标，只展示可用内容，
不出现版本、operation ID、停用按钮、容量配置或“管理”文案。两套页面可以复用 API Adapter 和纯展示组件，
不能复用同一页面状态机。

## 2. 当前接口可用性

### 2.1 管理端：现在可以接真实接口

当前 App API 已覆盖：

- 检查项目创建、详情、分页、修改、停用和恢复；
- 房间创建、详情、分页、修改、停用和恢复；
- 按房间查询、加入、停用和恢复检查项目关系；
- 房间一周七天 morning/afternoon 开放窗口与共享容量；
- 项目一周七天 morning/afternoon 预约开始、停止新增和结束时间；
- 乐观锁 `expected_version`、写操作 `operation_id` 和服务端严格包含校验。

管理端不再经过 Mock Adapter。开发环境没有数据时显示真实空状态，由有权限的工作人员创建测试项目和房间。

### 2.2 患者端：只完成展示规划

当前已有患者安全接口可以按已知 `item_id` 查询 active 房间，但还没有患者安全的“按科室列出 active 检查项目”
接口。管理端检查项目接口需要工作人员权限，患者端不得调用或尝试绕过。

因此患者端近期边界为：

- 页面与组件按真实业务模型改造，移除医生选择；
- 项目列表、日期和预约结果继续通过明确命名的 Patient Mock Adapter 提供；
- Mock 页面始终标识“演示数据，不会提交预约”；
- 不把 Mock 数据写入通用 API Cache 或长期 Storage；
- 后端补充患者项目目录和预约接口后，只替换 Adapter，不重写页面状态机。

后端后续至少需要提供：

```text
GET /api/v1/appointment/departments/:departmentId/examination-items
```

它只返回 active 项目的患者可见字段。真实预约阶段还需要候选日期/窗口、精确容量复核和创建预约接口。

## 3. Identity 是否参与

需要，但职责必须分清：

| 信息 | 来源 | 用途 |
|---|---|---|
| 当前账号、角色、permissions、工作人员所属科室 | Identity 会话 | 决定应用版本和管理入口 |
| 医院、院区、科室名称及稳定 ID | Identity 目录 API | 超管选择目标科室，页面展示“院区 / 科室” |
| 检查项目、房间、项目关系、周配置 | Appointment API | 实际业务读写 |

小程序只调用统一 App API，不直连 Identity RPC 或 Appointment RPC。Appointment 前端操作也不需要先向 Identity
“验证一次科室”：请求携带稳定 `department_id`，后端根据 Token 中的身份和科室范围再次鉴权。

具体规则：

- `department_doctor`：默认使用会话中的所属科室，不允许在页面切换到其他科室；为显示院区/科室名称，可从
  Identity 目录解析该 ID；
- `super_admin`：先通过 Identity 组织上下文选择“院区 / 科室”，再把稳定科室 ID 传给 Appointment；
- 患者：通过 Identity 公共目录选择院区和科室，再读取该科室患者可见项目；
- 科室名称只用于显示，不作为 Appointment 查询参数或缓存键。

## 4. 管理端请求顺序

```text
进入工作人员页面
 -> 从会话确定身份和 permissions
 -> 医生解析固定科室；超管加载院区和科室选择器
 -> 加载该科室房间第一页

选择房间
 -> 并行加载房间详情、房间项目关系、房间周配置

选择项目
 -> 加载项目详情与项目周配置
```

管理首页第三列必须来自所选房间的项目关系，不得用“按科室列出全部项目”替代。不得首屏加载全院所有房间、
项目和周配置。快速切换科室、房间或项目时使用请求 generation 或可取消请求，
迟到响应不得覆盖当前资源。

## 5. 客户端缓存与写后失效

后端 Redis 对前端透明。小程序只做内存级页面缓存，不长期保存业务事实：

- 项目列表：`department_id + status + page`；
- 房间列表：`department_id + status + page`；
- 房间项目：`room_id + status + page`；
- 项目可选房间：`item_id`；
- 房间周配置：`room_id`；
- 项目周配置：`item_id`。

| 写操作 | 前端必须失效 |
|---|---|
| 创建/修改/停用项目 | 科室项目列表、项目详情、项目可选房间、项目周配置 |
| 创建/修改/停用房间 | 科室房间列表、房间详情、房间项目与房间周配置 |
| 加入/停用/恢复关系 | 房间项目、项目可选房间 |
| 修改房间窗口 | 房间周配置及该房间相关候选预览 |
| 修改项目窗口 | 项目周配置及该项目相关候选预览 |

重新进入编辑页、服务端返回版本冲突、当前科室变化或账号权限变化时必须重新请求。

## 6. 写请求和错误处理

- 每次用户发起的新写操作生成 UUID `operation_id`；网络超时重试复用同一个 ID；
- 更新和状态变更携带页面当前 `expected_version`；
- `409/Aborted` 版本冲突时保留草稿，重新读取服务端事实，禁止自动覆盖；
- 严格窗口冲突时保留表单并定位 weekday/session，不在前端自动裁剪时间；
- `401` 进入统一单次刷新流程；`403` 关闭写入口并刷新身份；
- 停用、容量降低和会影响关联的修改必须二次确认；
- 不做创建、停用、关系变更和周配置保存的破坏性乐观更新。

## 7. 验收边界

- 管理端所有业务数据来自真实 Appointment API，不读取 Appointment Mock；
- 患者 Mock 与管理端真实 Adapter 完全隔离；
- 同名科室通过 `campus_id/department_id` 区分，写操作只使用稳定 ID；
- 房间与项目必须属于同一科室，页面不出现医生绑定；
- 房间开放时间和项目预约时间分开读取、编辑和失效；
- 患者端不能调用管理接口；管理端入口隐藏不替代服务端鉴权；
- 前端不会依据缓存自行确认预约或扣减容量。
