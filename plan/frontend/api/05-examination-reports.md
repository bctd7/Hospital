# 检查执行与报告接口消费

> 状态：已实现并完成前端 Adapter 验收（2026-08-15）。检查执行、报告模板、科室内患者搜索、
> 可读名称快照、报告发布/更正及患者查询均已接入真实接口。
>
> 接口事实源：`contracts/api/appointment-bookings.api` 与 `docs/api/openapi.json`。

## 1. 客户端边界

- 小程序只调用 App API，不直连 Appointment、Identity、MySQL 或 Redis；
- 工作人员操作使用 `report.read`、`report.publish`、`report.correct` 等既有 permission 控制入口，
  服务端仍对科室范围和每次写请求做最终鉴权；
- 患者读取依赖当前登录账号与预约归属，不要求患者拥有工作人员的报告 permission；
- 报告正文属于敏感业务数据，不写入 Storage，不进入前端日志、埋点、错误上报或页面路由参数；
- 首期不请求附件、影像、OSS、PDF、下载、打印、电子签章或多人审核接口。

## 2. 两套读取链路

### 2.1 患者端

患者报告列表只消费本人已正式发布的当前版本。列表分页加载，进入详情后按预约 ID 读取；草稿、历史版本和
其他患者报告不可见。患者侧不存在轮询草稿、推断报告是否完成或从“我的预约”拼接报告正文的逻辑。

### 2.2 工作人员端

工作人员从当前科室预约进入预约详情：

```text
confirmed -> 在项目时间内开始检查
in_progress -> 读取或创建草稿 -> 保存草稿 -> 完成并发布
completed -> 查看正式报告 -> 有权限时发起更正 -> 查看版本历史
no_show -> 只读查看未到场记录，不存在报告编辑入口
```

前端根据预约状态和 permission 显示操作，但不自行跳过状态。快速切换预约时使用请求序号丢弃迟到响应，
不让上一位患者的报告短暂出现在当前页面。

## 3. 写操作

- 开始检查、保存草稿、完成并发布、更正都使用稳定 `operation_id` 防止重复点击和网络重试重复执行；
- 保存草稿携带当前报告版本；完成并发布同时携带预约版本和报告版本；更正携带当前报告版本；
- 草稿正文只在当前页面内存中保留。离开存在未保存内容的页面必须确认，不做本地持久化“离线病历”；
- `409` 或版本冲突时停止写入，保留用户当前输入，并让用户选择重新加载服务端版本；不能静默覆盖；
- 首版发布前再次确认。成功后用服务端返回的正式报告替换页面状态，不从草稿自行合成成功结果；
- 更正从当前正式版本复制为新编辑缓冲区，必须填写更正原因；提交后产生新版本，原版不可在前端改写。

## 4. 加载、缓存与失效

- 预约列表、报告列表可做页面生命周期内的短缓存；报告正文只缓存于当前详情实例；
- 进入详情、下拉刷新、从编辑页返回以及应用从后台恢复时重新校验当前状态；
- 保存草稿后只更新当前预约的报告缓存；发布或更正后同时失效工作人员详情、版本历史和患者报告列表；
- `401` 进入统一单次 Token 刷新；`403` 关闭对应工作人员操作并返回安全页面；
- 工作人员读取尚无报告的 `404` 映射为“尚未填写报告”，患者详情的 `404` 映射为“报告尚未发布或不存在”，
  两者不能共用同一提示。

## 5. 已完成契约

预约列表使用服务端视图参数区分用户界面生命周期：`active` 只返回 `confirmed/in_progress`，`completed` 返回
`completed/no_show`。
患者端始终附加本人账号范围，工作人员端始终附加经授权的科室范围；前端不得通过获取全量后本地过滤代替。

工作人员报告列表支持 `keyword`，在科室范围内匹配患者展示名、手机号后四位和检查项目名称。患者报告列表仍只
返回本人已发布报告，不增加跨患者搜索能力。

前端不使用 Identity 目录手工拼接下列信息，App API 应返回页面可直接使用的 DTO：

1. 每个检查项目的报告模板读取、保存和乐观版本字段；
2. 工作人员预约列表中的患者可读名称，以及按患者名称或稳定患者标识搜索的服务端能力；
3. 报告中的科室名称、院区名称和工作人员显示名称。需要保留历史语义的字段应在发布时形成快照；
4. 如继续显示完整检查地址，报告 DTO 必须同时提供院区、楼栋、楼层和房间号，不能只返回院区 ID。

以上契约已由 Appointment 与 App API 提供。患者展示名和脱敏手机号在预约创建时写入快照；报告发布时保存科室、
院区和工作人员显示名快照。前端不使用账号 UUID、科室 UUID 或院区 UUID 作为面向用户的替代文案。

## 6. 测试边界

- API 映射覆盖四个预约状态、草稿/正式版/被替代版本和空可选字段；
- 验证患者无法读取草稿和历史版本，工作人员无法跨科室读取；
- 验证重复提交复用 operation ID，成功后才生成下一次 operation ID；
- 验证版本冲突不会丢失当前输入或覆盖服务端版本；
- 验证报告正文不会写入 Storage、日志和路由参数。
