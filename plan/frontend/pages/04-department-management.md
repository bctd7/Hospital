# 医院院区目录、科室医生目录与组织管理

> 状态：首期真实 HTTP 全链路已实现并联调；医院根节点保持只读
>
> 适用身份：患者、`department_doctor`、`super_admin`

## 1. 页面目标

本文只维护 Identity 的医院、院区、科室、医生目录与组织管理。患者端“挂号”和工作人员端“部门管理”
继续复用 `pages/registration/index` 路由，但不再假设两种身份使用同一业务主体：

- 患者端按“科室 → 检查项目 → 房间 → 本周窗口”选择预约资源，不按医生挂号；
- 工作人员端保留“唯一医院 → 当前院区 → 科室 → 医生”的组织管理，并增加 Appointment 房间和项目配置；
- Appointment 分为两套页面：[工作人员资源管理](./06-admin-appointment-resource-management.md)和
  [患者检查项目展示](./07-patient-examination-item-browser.md)，两者不共用业务主体或状态机。

Identity 目录部分按“唯一医院 → 当前院区 → 科室 → 医生”展示动态目录：

- 所有身份可以读取相同的有效组织目录；患者挂号流程不把医生作为预约资源；
- 患者只在需要浏览组织信息时只读；医生不能修改 Identity 组织结构；
- 超级管理员在相同主体上增加院区、科室维护和“用户管理”入口；
- 医院根节点只展示，不提供修改或切换；
- 首期科室必须直属院区，不展示或创建子科室。

所有数据来自后端组织与医生目录。前端消费策略见
[组织目录消费方案](../api/02-department-directory-and-management.md)，准确路径和字段以
[`contracts/api`](../../../contracts/api/) 与生成的 OpenAPI 为准；运行时不保留 Mock 数据源。

## 2. 手机页面布局

```text
┌─────────────────────────────┐
│ 演示医院                    │
│ 本部院区｜东院区｜西院区  ＋ │
├──────────┬──────────────────┤
│ 放射科   │ 林医生           │
│ 检验科   │ 周医生           │
│ 超声科   │ 李医生           │
└──────────┴──────────────────┘
```

- 医院名称位于页面标题区，从后端唯一医院根节点读取；
- 院区使用横向滚动的紧凑选择条，不把完整组织树塞进手机页面；
- 患者和医生只看到有效院区；超级管理员额外看到“管理院区”入口；患者挂号页不展示医生选择器；
- 选择院区后，左侧约 34% 显示该院区直属科室，右侧显示选中科室医生；
- 院区切换不发生页面跳转，恢复该院区上次选择的有效科室，否则选择第一个；
- 多个院区允许存在同名科室，页面状态和 key 始终使用稳定 ID；
- 院区或科室为空时展示真实空状态，不生成占位业务数据。

## 3. 身份与权限

### 3.1 患者和医生

- 可以读取医院、有效院区、有效科室及有效医生，但医生目录不参与 Appointment 预约选择；
- 可以切换院区、科室；
- 不显示新增、编辑、停用、恢复、移动等管理入口；
- 不通过隐藏路由、手势或长按提供写操作；
- 使用公共目录不代表获得工作人员或管理权限。

### 3.2 超级管理员

| 能力 | 前端判定 | 页面操作 |
|---|---|---|
| 维护院区和科室 | `identity.department.manage` | 新增、编辑、停用和恢复院区/科室，调整科室所属院区 |
| 进入用户管理 | `super_admin` 且具有 `identity.authorization.manage` 或 `identity.account.manage` | 顶部显示“用户管理”入口 |

医院名称对超级管理员同样只读。前端权限只控制入口可见性；后端必须对每次写请求重新鉴权。

## 4. 加载和选择流程

1. 页面进入时请求组织上下文，得到唯一医院和有效院区；
2. 按“上次选择且仍有效的院区 → 当前医生所属科室的院区 → 第一个有效院区”选择院区；
3. 携带 `campus_id` 请求该院区直属科室；
4. 按“该院区上次选择的科室 → 当前医生所属科室 → 第一个有效科室”选择科室；
5. 携带 `department_id` 分页请求医生；
6. 快速切换院区或科室时使用不同请求序号，丢弃迟到响应。

不得首屏一次性加载所有院区的所有科室和医生。院区、科室和医生分别按层级懒加载及缓存。

## 5. 管理交互

### 5.1 院区管理

“管理院区”打开独立弹层或二级页面，避免把所有操作挤在横向选择条中：

- 列出有效和已停用院区；
- 新增院区时只填写名称，父节点固定提交后端返回的唯一 `hospital_id`；
- 编辑院区只修改名称，不允许移动父节点；
- 停用院区需要独立确认；存在有效科室时后端拒绝，前端提示先处理科室；
- 停用不级联科室，恢复时医院根节点必须有效；
- 医院根节点不出现编辑、停用或删除按钮。

### 5.2 科室管理

- 新增科室必须基于当前选中院区，明确提交 `parent_id=campus_id`；
- 编辑科室可以修改名称，或明确选择另一个有效院区调整归属；
- 移动科室成功后同时失效原院区和目标院区缓存；
- 停用科室前必须先调岗或撤销有效医生身份；
- 已停用科室通过管理员视图查询和恢复；
- 不提供“新增子科室”或把科室挂到科室下的入口；
- 所有写入等待服务端成功，不进行破坏性乐观更新。

### 5.3 医生和用户管理

- 医生列表不放置调岗、撤销身份、禁用账号等行内按钮；
- 患者和医生只读浏览医生摘要；
- 超级管理员可从医生行进入用户详情；
- 开通医生、调岗、撤销医生身份和账号启停继续在独立用户详情页完成。

## 6. 组件和状态边界

```text
OrganizationDirectoryPage
├── HospitalHeader                   // 所有身份，只读
├── CampusSelector                   // 所有身份，有效院区
├── CampusManager                    // 仅超级管理员按权限挂载
├── DepartmentSidebar
│   └── DepartmentEditorDialog       // 仅超级管理员按权限挂载
├── DepartmentDoctorPanel
└── AdminUserManagementEntry         // 仅超级管理员按权限挂载
```

- 页面容器编排组织上下文、当前院区、当前科室、请求序号和缓存失效；
- 展示组件只接收 props/emit，不直接调用 `uni.request`；
- API 层分别暴露组织上下文、按院区科室、按科室医生及管理员组织方法；
- 院区缓存使用 `campus_id`，医生缓存使用 `department_id + page`；
- 不以医院、院区、科室或医生名称作为业务标识；
- 医生列表不展示完整手机号等敏感字段。

## 7. 页面状态

必须覆盖：

- 组织上下文首屏加载和失败重试；
- 无有效院区、院区无科室、科室无医生；
- 院区切换时科室局部加载、科室切换时医生局部加载；
- 快速切换时旧响应被丢弃；
- 当前院区或科室被其他管理员停用后的自动回退；
- 新增、编辑、移动、停用、恢复的提交中、版本冲突、层级错误和权限错误；
- 网络恢复后重新拉取，不把旧缓存误认为写入成功。

## 8. 验收标准

- 患者端底栏仍为“挂号”，工作人员端仍为“部门管理”，两者复用路由和外壳但使用不同业务主体；
- 页面动态显示唯一医院名称和有效院区选择器；
- Identity 组织视图切换院区只显示直属科室，切换科室只显示该科室医生；患者挂号视图改为显示检查项目；
- 患者和医生看不到、也无法调用组织管理操作；
- 超级管理员能管理院区和科室，但不能管理医院根节点；
- 新增科室必须明确关联当前院区，不能依赖后端默认院区；
- 首期不能创建子科室；
- 有有效科室的院区、有有效医生的科室不能直接停用；
- 移动科室、调岗或撤销医生后相关缓存准确失效；
- 医生身份和账号操作仍只出现在用户详情页；
- 空状态、失败重试、分页、权限变化和并发版本冲突均可验证。
