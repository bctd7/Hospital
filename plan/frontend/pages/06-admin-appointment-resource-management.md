# 工作人员检查项目与预约资源管理

> 状态：第一版已实现并接入真实 Appointment API
>
> 适用身份：`department_doctor`、`super_admin`

## 1. 页面目标

工作人员端是管理页面，以科室为边界维护检查项目、房间、房间可执行项目和两套周配置。推荐从截图首页的
“检查项目管理”卡片进入独立二级页，工作人员“部门管理”Tab 同时保留快捷入口。

患者端不会复用该页面；患者版本首页对应入口改成“检查项目”或“预约检查”，不出现“管理”二字。

管理结构固定为：

```text
当前科室
├── 检查项目
│   ├── 项目基本信息
│   ├── 项目状态
│   └── 项目周预约窗口
└── 房间资源
    ├── 房间基本信息
    ├── 可执行检查项目
    └── 房间周开放窗口与共享容量
```

## 2. 已实现路由

```text
pages/admin/appointment/index             管理首页：检查项目 / 房间资源
pages/admin/appointment/item-detail       项目详情、编辑和项目周配置
pages/admin/appointment/room-detail       房间详情、项目关系和房间周配置
```

手机端管理首页通过 Tab 分开项目与房间列表，详情页负责单资源编辑；返回列表时只刷新受影响项。

## 3. 身份和科室上下文

### 3.1 科室医生

- 页面顶部只读显示 Identity 解析出的“院区 / 科室”；
- Appointment 查询固定使用会话所属 `department_id`；
- 不显示科室切换器，也不允许通过路由参数管理其他科室。

### 3.2 超级管理员

- 首次进入先加载 Identity 组织上下文；
- 使用“院区 -> 科室”两级选择器，不提供全院同名科室平铺列表；
- 科室选择完成后才加载 Appointment 数据；
- 切换科室前若存在未保存草稿，必须确认放弃；切换后清空项目、房间和配置状态。

## 4. 检查项目列表与编辑

列表顶部提供 active/disabled 筛选、名称展示和新建按钮。每项展示：

```text
项目名称
说明摘要
状态
更新时间
```

不直接展示 UUID 和 version；它们保存在页面状态中供请求使用。

项目详情包括：

- 名称；
- 检查说明；
- active/disabled 状态；
- 项目周预约配置入口；
- 停用或恢复操作。

新建和修改成功后返回服务端对象替换本地详情，并失效当前科室列表。停用不是删除；disabled 项目仍可通过
筛选查看和恢复。

## 5. 房间列表和项目关系

管理端房间视角严格表达为：

```text
A 科室
├── 房间 A
│   ├── CT
│   └── 全景片
└── 房间 B
    └── CT
```

房间列表展示名称、状态和已关联项目数量。进入房间后：

- 编辑房间名称；
- 停用或恢复房间；
- 分页查看已加入项目；
- 从当前科室 active 项目中选择并加入；
- 停用或恢复已有关系。

加入项目选择器必须排除其他科室项目和已经存在的关系；提交时仍以服务端校验为准。一个房间可以加入多个
项目，一个项目也可以加入多个本部门房间，不出现医生字段。

## 6. 两套周配置编辑器

两个编辑器视觉语言可以一致，数据模型不能混用：

```text
RoomWeeklyWindowEditor
  weekday + session + open_time + close_time + active_capacity

ItemWeeklyWindowEditor
  weekday + session + start_time + booking_cutoff_time + end_time
```

- 固定显示周一至周日；
- 每天固定 morning、afternoon 两行；
- 每行最多一个连续窗口，不提供“再加一个时段”；
- 未配置行显示“未开放/不可预约”；
- 保存提示“从本周立即生效，后续周继续沿用”；
- 不提供节假日、单日覆盖、未来周模板或医生排班；
- 前端可预检项目窗口是否落在房间窗口内，服务端仍是最终裁决者。

关闭已有行调用 disable 接口，不把空时间提交成更新。编辑已有行携带 window ID 和版本，新建行不携带
window ID 且版本为 0。

## 7. 页面状态

每个列表或详情必须独立覆盖：

- 首屏加载、下拉刷新、分页追加和分页失败重试；
- 科室没有项目、没有房间、房间没有项目关系、资源没有周配置；
- 表单提交中、重复点击保护、提交成功；
- 参数错误、无权限、不存在、同名冲突、版本冲突和窗口包含冲突；
- 当前资源被其他管理员停用；
- 快速切换资源时旧响应被丢弃；
- 离开或切换科室时未保存草稿确认。

管理页面不以 Mock 填充空状态。真实数据库为空时，引导有权限的用户点击“新建检查项目”或“新建房间”。

## 8. 实现顺序

1. 建立真实 Appointment API Adapter、请求/响应类型和错误映射；
2. 接入 Identity 会话与科室上下文；
3. 完成检查项目列表、新建、详情、修改、停用和恢复；
4. 完成房间列表和房间 CRUD；
5. 完成房间项目关系管理；
6. 完成房间周配置编辑器；
7. 完成项目周配置编辑器；
8. 补齐并发版本冲突、权限变化和缓存失效测试。

检查项目管理是第一批交付；后续步骤可以在同一管理框架内逐项开启，不阻塞项目 CRUD 上线。

## 9. 验收标准

- 医生只能管理所属科室，超管明确选择院区和科室；
- 管理端全部读取真实 API，不调用 Appointment Mock；
- 项目 CRUD、状态切换和版本冲突流程完整；
- 房间视角正确展示多个项目，一个项目可以属于多个房间；
- 房间和项目两套周配置不会混写；
- 不出现医生绑定、自动房间分配、节假日或拆分小窗口；
- 页面刷新、空状态、失败重试和写后缓存失效可验证。
