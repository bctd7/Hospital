# 微信小程序前端外壳设计

> 文档状态：初稿
>
> 适用阶段：前端第一阶段——可切换的空白页面框架
>
> 参考界面：用户提供的医院小程序“我的”页面截图
>
> 技术方向：uni-app + Vue 3 + TypeScript + Vite

## 1. 设计目标

第一阶段只建立稳定、可扩展的应用外壳，不实现身份验证、挂号、消息中心、预约列表等具体业务。

需要交付：

1. 建立微信小程序工程基础结构。
2. 在底部提供四个一级入口，用户点击后可以自由切换页面。
3. 每个一级入口先使用独立的空白占位页，后续业务可以逐页接入。
4. 建立统一的页面布局、颜色、间距、安全区和状态占位规范。
5. 预留 API、身份会话、全局状态和前端类型目录，但第一阶段不发起业务请求。

第一阶段不包含：

- 微信身份验证和 Token 管理；
- 挂号、医生、排班、预约等业务接口；
- 消息列表、未读数量和订阅通知；
- 页面中的业务卡片和列表；
- 动态权限菜单；
- 后台配置底部导航。

## 2. 参考界面拆解

参考图可以拆分为三层：

```text
系统层：微信状态栏、胶囊按钮和安全区域
应用内容层：用户信息、业务卡片、常用工具等可滚动内容
应用导航层：固定在底部的首页、挂号、消息、我的
```

第一阶段只实现应用导航层和空白的应用内容层。参考图中的头像、身份提示、预约状态、工具入口等都属于后续业务模块，不放进基础外壳。

视觉上先保留以下原则：

- 页面使用浅灰背景，内容区后续可以承载白色卡片；
- 选中的底部入口使用医疗蓝强调色；
- 未选中的入口使用中性灰；
- 底部区域适配全面屏安全区；
- 尺寸使用适合小程序的响应式单位，不按截图像素硬编码；
- 颜色、圆角、阴影、间距统一通过设计变量管理。

参考图只作为信息层级和交互方式参考，不直接复制其中的品牌、图标或业务内容。

## 3. 一级页面与导航

首版固定四个一级页面：

| 顺序 | 页面 | 路由 | 第一阶段内容 | 后续职责 |
|---|---|---|---|---|
| 1 | 首页 | `pages/home/index` | 空白占位 | 公告、预约摘要、快捷入口 |
| 2 | 挂号 | `pages/registration/index` | 空白占位 | 科室、检查项目、排班、预约流程 |
| 3 | 消息 | `pages/messages/index` | 空白占位 | 预约提醒、系统通知、公告、未读状态 |
| 4 | 我的 | `pages/profile/index` | 空白占位 | 预约记录、就诊人、个人资料、常用工具 |

一级入口保持少而稳定。医生列表属于挂号或业务详情流程，不再占用底部一级入口；医生详情、预约确认和消息详情等页面使用普通页面跳转。

### 3.1 导航实现决策

第一阶段使用 uni-app `pages.json` 中的标准 `tabBar` 配置，不实现自定义 TabBar。

原因：

- 不依赖后端即可工作；
- 行为符合微信小程序的系统预期；
- 页面切换链路简单、稳定；
- 能满足四个固定一级入口和选中态切换；
- 可以先验证整体信息架构，避免过早引入自定义导航状态同步问题。

只有出现以下明确需求时，才评估自定义 TabBar：

- 中间入口需要突出、悬浮或使用特殊形状；
- 导航需要超出标准样式的动画；
- 不同角色需要完全不同的导航结构；
- 标准 TabBar 无法满足已确认的无障碍或品牌要求。

即使未来更换为自定义 TabBar，四个一级页面的路由和页面内部业务模块仍应保持不变。

### 3.2 消息入口边界

“消息”作为稳定一级入口，但第一阶段只显示占位状态：

- 不请求消息列表；
- 不展示模拟未读数量；
- 不在应用启动时轮询消息；
- 不要求用户完成身份验证后才能进入；
- 不因为后端消息服务未实现而影响其他页面切换。

未来后端提供未读数量后，由统一会话或消息 Store 更新 TabBar 角标。消息正文、已读状态和通知权限在独立的消息中心规划中设计。

## 4. 前端工程结构

建议在 `apps/miniapp/` 中形成以下结构：

```text
apps/miniapp/
├── src/
│   ├── api/
│   │   ├── client.ts              # 统一请求入口，后续实现
│   │   └── modules/               # 按业务域拆分接口
│   ├── components/
│   │   ├── layout/                # 页面通用布局
│   │   └── states/                # 空白、加载、错误等状态
│   ├── config/                    # 环境和非敏感配置
│   ├── pages/
│   │   ├── home/index.vue
│   │   ├── registration/index.vue
│   │   ├── messages/index.vue
│   │   └── profile/index.vue
│   ├── static/
│   │   └── tabbar/                # 底部导航本地图标
│   ├── stores/
│   │   ├── session.ts             # 后续身份会话状态
│   │   └── messages.ts            # 后续消息和未读状态
│   ├── styles/
│   │   ├── tokens.scss            # 颜色、间距、圆角等变量
│   │   └── global.scss            # 全局基础样式
│   ├── types/                     # 前端公共类型
│   ├── utils/                     # 无业务状态工具
│   ├── App.vue
│   ├── main.ts
│   ├── manifest.json
│   └── pages.json
├── package.json
├── tsconfig.json
└── vite.config.ts
```

工程约束：

- 页面只负责展示和交互编排，不直接散落网络请求配置；
- 业务请求集中放在 `api/modules/`；
- 请求和响应类型集中维护，避免页面重复声明同一结构；
- TabBar 页面和图标在一个位置集中配置，不在页面中复制导航；
- TabBar 图标使用本地资源，应用主导航不依赖网络图片；
- App 启动不因为可选业务请求失败而阻塞页面外壳；
- AppSecret、数据库地址和后端内部地址禁止进入前端；
- 第一阶段只建立必要目录，不添加没有实际用途的复杂依赖。

## 5. 页面外壳设计

每个一级页面遵循相同的基础结构：

```text
Page
├── 系统安全区
├── 可选页面标题区域
├── 可滚动内容区域
│   └── 第一阶段空白占位
└── 系统 TabBar 与底部安全区
```

第一阶段的占位页只需要表现出当前所在页面，例如页面名称和“功能建设中”。占位内容不能模拟真实医疗数据，也不应为了看起来完整而写死预约、消息或用户信息。

后续页面内容以模块形式加入内容区域，不修改应用导航层。例如“我的”页面可以逐步添加：

```text
profile 页面
├── 用户摘要模块
├── 就诊人管理模块
├── 我的预约模块
└── 常用工具模块
```

## 6. 状态与路由边界

### 6.1 第一阶段状态

第一阶段只有纯前端状态：

- 当前选中的底部入口；
- 页面自身的临时展示状态；
- 主题和安全区样式。

标准 TabBar 负责一级入口切换，不额外创建一套重复的全局导航状态。

### 6.2 后续身份状态

后续身份状态由统一的 `session` Store 管理，但不应让应用外壳强制要求用户完成验证后才能切换页面。身份验证界面由就诊人管理页面单独设计，不建立独立页面或入口。

建议行为：

- 未验证身份的用户仍可以进入四个一级页面；
- 页面中的受保护业务操作引导至就诊人管理流程；
- Token 过期由统一 API Client 处理；
- 页面不各自实现一套身份判断和刷新逻辑。

### 6.3 详情页跳转

底部导航只承载一级页面。医生详情、预约确认、消息详情等页面使用普通页面跳转，并提供清晰的返回路径。

## 7. 与后端接口的关系

### 7.1 第一阶段结论

可切换的空白页面框架不涉及后端数据接口。

本阶段不需要修改：

- `contracts/api/` 中的接口契约；
- Go Handler、Logic 或 Model；
- 数据库表；
- Redis 或 Kafka；
- 微信身份验证服务；
- 消息服务和未读数量接口。

底部导航项、路由、图标和页面名称作为前端发布内容维护，不为了四个稳定入口设计“导航配置接口”。这样可以避免网络异常导致应用主导航不可用，也可以保持微信小程序版本审核内容与实际导航一致。

### 7.2 后续需要后端的内容

| 能力 | 是否需要后端 | 预计接口方向 |
|---|---|---|
| 四个空白页切换 | 否 | 无 |
| 页面主题与基础布局 | 否 | 无 |
| 微信用户身份验证 | 是 | 临时凭证换码、业务 Token |
| 用户头像和资料 | 是 | 用户资料查询与更新 |
| 预约状态摘要 | 是 | 预约列表、预约状态统计 |
| 科室、项目、医生和排班 | 是 | 挂号业务查询 |
| 挂号与取消预约 | 是 | 预约创建、取消、幂等控制 |
| 消息列表与未读角标 | 是 | 消息列表、未读数量、已读操作 |
| 微信订阅通知 | 是 | 订阅授权记录、通知任务和发送结果 |
| 隐私协议内容 | 视方案而定 | 可随版本内置，也可由后端提供版本化内容 |

### 7.3 不建议的首版设计

第一阶段不从后端动态下发底部导航结构。如果未来出现多角色或多机构差异，优先由后端下发“能力和权限”，前端根据已发布页面决定入口状态；不要让后端下发任意路由地址。

## 8. 后续接口接入原则

业务接口开始接入时遵守：

1. 先在 `contracts/api/` 定义版本化请求与响应。
2. 前端类型与接口契约保持一致，不直接依赖数据库字段。
3. API Client 统一添加 Token、请求 ID、超时和错误转换。
4. 页面明确区分加载、成功、空数据、业务失败和网络失败。
5. 医疗和身份敏感数据只获取完成当前功能所必需的最小集合。
6. 本地和预发使用模拟或脱敏数据，不在日志中输出 Token、微信临时 code 或完整敏感资料。

健康检查接口可以在框架完成后用于验证小程序到 Go 服务的网络链路，但它不是底部导航和空白页运行的前置条件。

## 9. 第一阶段验收标准

完成实现后应满足：

- 项目可以编译为微信小程序并被微信开发者工具打开；
- 底部按顺序显示首页、挂号、消息、我的四个入口；
- 点击任一入口可以进入对应的独立页面；
- 当前入口具有清晰的选中态，其他入口为未选中态；
- 页面切换不发起任何业务网络请求；
- 消息页不展示虚假的消息或未读数量；
- 四个页面均可独立扩展，不需要复制导航或全局样式代码；
- 页面与底部区域适配全面屏安全区；
- 不出现内容被 TabBar 遮挡、重复导航或明显跳动；
- TypeScript 检查和小程序构建通过；
- 不包含 AppSecret、真实 Token 或其他敏感配置。

建议至少在一种普通屏幕尺寸和一种全面屏尺寸下检查布局。

## 10. 迭代顺序

```text
M1：初始化 uni-app + Vue 3 + TypeScript 工程
    -> 建立主题变量和目录结构
    -> 实现首页、挂号、消息、我的四个空白一级页面
    -> 配置标准 TabBar
    -> 微信开发者工具预览和尺寸检查

M2：连接现有健康检查接口
    -> 建立 API Client
    -> 验证本地开发网络链路

M3：实现微信登录与 Hospital 会话
    -> 参照 04-login-and-identity-implementation.md
    -> Token 生命周期和账号 Principal

M4：在就诊人管理中完成本人基础身份
    -> 参照 05-self-patient-basic-identity.md
    -> PNVS 已验证手机号 + 本人资料（当前方案，详见 07）

M5：按业务优先级逐条接入挂号、消息和个人中心功能
```

当前只批准和实施 M1 时，不需要等待任何后端业务接口。

## 11. 待业务阶段确认的事项

以下内容不会阻塞第一阶段，但应在对应业务开始前确认：

1. 首条核心业务链路是“选择检查项目”“选择科室”还是其他入口；
2. 是否允许访客浏览项目、医生和排班；
3. 用户角色是否只有患者，还是还包含医生或院内工作人员；
4. 消息入口包含哪些消息类型以及消息保留期限；
5. 未读数量采用进入页面刷新、应用恢复刷新还是其他策略；
6. 品牌主色、Logo、正式图标和字体规范；
7. 医疗与个人信息的展示范围、缓存限制和隐私要求。
