# 微信资料进入页与“我的”页面改版需求

> 文档状态：需求已确认，前端静态能力已实施
>
> 适用范围：微信小程序前端入口、主应用跳转及“我的”页面
>
> 需求优先级：本文件与既有个人中心文档冲突时，以本文件为准

## 1. 改版目标

小程序调整为前后两层：

1. 第一层保留参考图一的简洁资料填写界面，允许用户选择微信头像并填写或选用微信昵称；
2. 用户点击进入后，无论资料是否填写完整、OpenID 换取是否成功，都可以进入主应用；
3. 第二层继续使用“首页 / 挂号 / 消息 / 我的”四个固定底部入口；
4. “我的”页面按照参考图二重新布局，展示用户资料头部和六个功能入口；
5. 当前需求不把微信昵称、头像或 OpenID 解释为患者实名身份。

## 2. 名词与业务边界

### 2.1 微信展示资料

微信展示资料仅包括：

- 用户主动选择的头像；
- 用户主动填写或选用的昵称。

这些内容只用于界面展示，不代表真实姓名、患者身份、就诊人身份或实名认证结果。

### 2.2 OpenID

OpenID 是微信用户在当前小程序下的平台标识，用于后端区分小程序账号，但不是医疗业务身份，也不能单独证明用户真实姓名或患者身份。

小程序端调用 `wx.login` 或 `uni.login` 后只能获得临时 `code`。安全链路必须为：

```text
小程序调用 wx.login / uni.login
  -> 获得临时 code
  -> 将 code 发送给 Hospital 后端
  -> 后端携带 AppID 和 AppSecret 调用微信 code2Session
  -> 后端获得 OpenID 和 session_key
  -> 后端建立自己的匿名账号或业务会话
  -> 小程序只接收 Hospital 会话凭证和必要的用户摘要
```

约束：

- 小程序前端不直接安全地获得 OpenID；
- AppSecret 不得写入前端源码、构建产物或网络请求；
- `code` 只能使用一次且不长期保存；
- `session_key` 不返回前端、不写日志；
- OpenID 不作为页面展示字段；
- 微信资料填写与 OpenID 换取是两个独立过程，任何一项都不应被描述为患者身份认证。

### 2.3 后续医疗身份

真实姓名、证件信息、患者档案和就诊人绑定属于后续医疗业务。其采集、验证和展示规则不在本入口页处理，应在对应业务需求确认后单独设计。

## 3. 第一层：微信资料进入页

### 3.1 页面定位

该页面是进入主应用前的资料填写页，不命名为登录页、认证页或身份初始化页。

首版路由建议为：

```text
pages/entry/index
```

### 3.2 页面内容

参考图一保留以下布局：

- 顶部小程序标题；
- 居中的头像选择区域；
- 一行昵称输入区域；
- 底部主按钮。

主按钮文案使用“进入小程序”，不继续使用示例中的“Hello World”。

头像使用微信小程序的头像选择能力；昵称输入使用适合微信昵称填写的输入能力。头像和昵称均为可选项，不要求用户必须填写。

### 3.3 进入行为

用户点击“进入小程序”后：

1. 前端可尝试调用 `uni.login` 获取临时 `code`；
2. 如果后端接口已经实现，则把 `code` 交给后端换取应用会话；
3. 保存用户主动选择的头像和昵称，用于当前端展示；
4. 无论资料是否填写、网络是否可用、OpenID 换取是否成功，最终都进入主应用首页；
5. 跳转目标为 TabBar 首页，使用 `switchTab`，不在页面栈中保留重复的主页面。

失败时只记录当前处于“无应用会话”状态，不得把失败包装成成功，也不弹出阻塞用户进入主应用的强制提示。

### 3.4 默认展示

当用户没有提供资料时：

- 头像使用本地默认头像；
- 昵称显示“微信用户”；
- 用户仍可查看主应用页面；
- 后续确实依赖账号或医疗身份的业务，由对应页面单独说明和引导。

## 4. 第二层：主应用外壳

底部四个一级入口保持当前工程配置，不因参考图二而改变：

| 顺序 | 名称 | 路由 |
|---|---|---|
| 1 | 首页 | `pages/home/index` |
| 2 | 挂号 | `pages/registration/index` |
| 3 | 消息 | `pages/messages/index` |
| 4 | 我的 | `pages/profile/index` |

参考图二底部出现的“资讯”等文案仅作为视觉参考，不进入本次需求。

## 5. “我的”页面改版

### 5.1 头部

“我的”页面头部按照参考图二呈现：

- 蓝色背景和波形装饰；
- 左侧展示头像；
- 中间展示昵称；
- 右侧展示“账号设置”入口。

头像和昵称优先读取第一层页面中用户主动提供的展示资料；没有资料时使用默认头像和“微信用户”。头部不展示 OpenID、真实姓名、证件信息或患者认证状态。

### 5.2 功能入口

本次设计变更后，“我的”页面恢复参考图二中的六个入口：

1. 就诊人管理；
2. 我的预约；
3. 候补订单；
4. 我的关注；
5. 设置；
6. 消息管理。

入口采用统一的配置数组和可复用菜单组件渲染。首版可以进入静态二级页面，但不得伪造真实订单、消息或患者数据。

“设置”行可展示清除缓存、联系客服、用户隐私协议和账号注销等摘要，具体操作在对应需求确认后实现。

### 5.3 账号设置入口

“账号设置”是普通功能入口，不代表用户已完成患者身份认证。首版只预留路由和静态页面；后续可承载展示资料修改、会话状态和账号操作，但医疗身份仍归属就诊人相关业务。

## 6. 页面状态

入口页至少区分以下状态，但不需要全部显示给用户：

| 状态 | 进入主应用 | “我的”头部 |
|---|---|---|
| 已填写头像和昵称，应用会话建立成功 | 允许 | 展示所填资料 |
| 已填写头像和昵称，应用会话建立失败 | 允许 | 展示所填资料 |
| 未填写资料，应用会话建立成功 | 允许 | 默认头像 + 微信用户 |
| 未填写资料，应用会话建立失败 | 允许 | 默认头像 + 微信用户 |

OpenID 换取失败不影响页面浏览；真正需要账号、预约或患者身份的写操作，在对应业务页面中处理不可用状态。

## 7. 前后端边界

### 7.1 纯前端可先实现

- 入口页布局；
- 头像选择和昵称填写；
- 本地默认资料；
- 点击后进入主应用；
- 四个 TabBar 页面切换；
- “我的”页面头部与六个静态入口；
- 各二级页面的静态空状态。

### 7.2 获取 OpenID 时必须有后端

- 接收小程序临时 `code`；
- 调用微信 `code2Session`；
- 保存 OpenID 与内部账号的映射；
- 签发 Hospital 自己的会话凭证；
- 处理微信接口失败、超时和 `code` 失效；
- 保证 AppSecret 和 `session_key` 只存在于服务端安全环境。

后端接口完成前，前端可以完成资料展示和页面跳转，但不能声称已经获得或绑定 OpenID。

## 8. 非本次范围

- 患者实名验证；
- 身份证或手机号认证；
- 就诊卡绑定；
- 真实预约、候补订单和消息数据；
- 微信支付；
- 强制授权头像或昵称；
- 因微信会话失败而阻止用户浏览主应用；
- 把 AppSecret 或 `session_key` 放入小程序。

## 9. 验收标准

- 第一层页面视觉结构与参考图一一致，按钮文案为“进入小程序”；
- 用户可以选择头像、填写或选用昵称，也可以直接跳过；
- 任一资料和会话结果都不阻塞进入主应用；
- 主应用底部仍为“首页 / 挂号 / 消息 / 我的”；
- “我的”页面呈现参考图二的头部结构；
- “我的”页面显示六个规定入口；
- 未提供资料时显示本地默认头像和“微信用户”；
- 页面不展示 OpenID、session_key 或医疗身份状态；
- 前端代码和构建产物不包含 AppSecret；
- 后端未接入时不得显示“OpenID 已绑定”等误导状态；
- TypeScript 检查和微信小程序构建通过。

## 10. 实施顺序

前端静态实现按以下顺序交付：

1. 调整入口路由和资料进入页；
2. 建立可选展示资料状态；
3. 调整进入主应用的容错跳转；
4. 按参考图二重构“我的”页并恢复六个入口；
5. 补齐静态二级页面；
6. 完成前端检查和微信开发者工具验收；
7. 后端接口明确后，再单独接入 OpenID 换取与应用会话。

当前第 1 至第 6 项已完成；第 7 项仍属于后续前后端联调范围。
