# 身份驱动的应用版本选择

> 文档状态：患者端已实现，工作人员后台仅实现空白身份占位页
>
> 适用范围：普通用户、部门医生、超级管理员

## 1. 核心决策

界面不是“就诊状态”，也不是用户可以随意修改的本地模式。登录后由 Identity 返回的角色决定
账号对应的目标应用版本：

```text
普通用户
  -> patient 应用

department_doctor / super_admin
  -> 同一套 staff 工作人员后台
```

医生和超级管理员不维护两套后台。两者看到的功能差异来自 `permissions`，所有敏感操作仍由后端
鉴权；前端隐藏按钮不能代替授权。

## 2. 当前发布边界

工作人员后台业务尚未开始实现，当前只开启一个无 TabBar 的空白身份占位页。医生和超级管理员
登录后进入同一个页面，只显示“医生”或“超级管理员”的当前身份提示，不展示伪造业务数据。

前端在 `src/utils/appShell.ts` 预留以下集中入口：

- `resolveIdentityAppVariant`：把用户角色解析成 `patient` 或 `staff` 目标版本；
- `resolveAppVariant`：结合工作人员后台开关，决定当前真正启用的版本；当前开关只启用占位页；
- `applyAppVariantNavigation`：应用对应版本的 TabBar 文案；
- `hasIdentityPermission`：按 permission 判断工作人员功能是否可见。

后台页面树完成后，从同一个 `staff` 边界继续扩展，不应在各页面散落角色判断。

## 3. 角色与权限

```text
roles
  -> 选择 patient / staff 应用版本

permissions
  -> 决定 staff 后台内具体模块、菜单和操作按钮

后端鉴权
  -> 决定请求最终能否执行
```

例如，医生可以具有预约读取权限，超级管理员可以具有账号管理权限；两者仍复用同一个工作人员
后台布局和路由体系。

## 4. 会话规则

`appVariant` 是从当前 `principal.roles` 派生的运行时状态，不写入数据库，也不作为授权事实。
登录、恢复 Session、刷新 Token 后都重新解析。退出登录后回到 `patient`。

旧版本存储中的 `activeMode` 被忽略，不再提供“患者端/医生端”手动切换按钮。

## 5. 就诊人页面边界

“就诊人管理”只管理本人展示资料和已验证手机号，不再提供“启用/停用本人就诊信息”的状态
开关。应用版本选择与就诊资料是两件不同的事情。

## 6. 验收标准

- 普通用户目标版本解析为 `patient`；
- `department_doctor` 与 `super_admin` 都解析为同一个 `staff`；
- 工作人员身份进入同一个空白 `staff` 占位页，且不显示患者端 TabBar；
- 后台框架开始建设后，不需要修改 Session 或登录身份判断即可继续扩展 `staff`；
- 医生和超级管理员的差异只按 permissions 展示，并由后端再次鉴权；
- 就诊人页面不存在身份或就诊状态切换开关。
